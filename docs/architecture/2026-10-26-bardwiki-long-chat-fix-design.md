## 단계 1. 조용한 손실 멈추기

가장 작고 효과가 큰 변경이다. 여기까지만 해도 "모르는 사이에 빠지는" 경로가 대부분 막히고, 이후 단계의 효과를 잴 계측이 생긴다.

### A. 분석 입력 조립기 (약점 1)

지금은 `fitAnalysisInput`(`src/ts/risubard/memoryAnalysisClient.ts:155`)이 완성된 JSON의 가장 긴 문자열을 잘라 맞춘다. 이것을 "무엇을 넣을지 우선순위로 고르는 조립기"로 바꾼다.

- 예산 = 상한 - 시스템 지시문 토큰 - 출력 여유. 배치 분할(`risubard-memory-analysis.ts:159`)도 같은 예산을 쓴다.
- 필수 자료: 확정 원문(`confirmedMessages`), 정본 재작성 대상의 전문. 절대 자르지 않는다.
- 선택 자료: 기존 정본 전문, 참고 발췌(`existingNotes`), 로어 참고, 직전 사건 요약. 우선순위 낮은 것부터 항목 단위로 통째로 뺀다. 문자열 중간을 자르지 않는다.
- `AI 분석 토큰 상한`의 뜻을 "참고 자료 상한"으로 바꾼다. 시스템 지시문과 필수 자료는 상한과 무관하게 항상 온전히 보내고, 상한은 선택 자료가 들어갈 자리만 정한다. 기본값 8,192는 그대로 둔다(사용자 결정 2026-10-26).
  - 비용 영향: 상한 안에 들어가던 턴은 지금과 같다. 늘어나는 것은 지금 잘려 버려지던 긴 턴의 그 부분뿐이다. 그 턴의 원문은 분석에 꼭 필요한 최소량이다.
  - 상한에 비례해 커지던 선택 자료 몫(기존 정본 전문은 상한의 1/4, 참고 발췌는 상한 x 2 - 8,000자)은 고정값으로 떼어 내, 상한을 올려도 매 턴 비용이 따라 오르지 않게 한다.
  - 공급자 문맥 한도를 넘는 극단적인 턴만 `AnalysisInputTooLarge`로 실패시키고 영수증에 이유를 남긴다. 이 턴은 B의 밀린 턴 목록에 보인다.
- 선택 자료를 뺀 경우는 영수증 메모에 남긴다("로어 참고 2개 제외" 같은 식). 벤치마크와 테스터 제보에서 바로 보인다.
- 매 호출 고정 비용인 시스템 지시문(기본 프리셋 약 5천 토큰: 작성 계약 1,307, 분석 가이드 2,181, 정본 정책 865 등)을 따로 줄인다. 겹치는 지시를 합치는 것만으로도 줄일 여지가 있다. 저가 장기챗 컨셉에서는 상한보다 이쪽이 실제 비용을 정한다.

공식 계약 영향: `bounded_context_architecture.md`의 "구조화된 필드의 긴 본문과 후보 문서를 먼저 축소"를 "선택 자료를 항목 단위로 빼고, 확정 원문과 재작성 대상은 줄이지 않는다"로 고쳐야 한다.

### B. 채팅별 분석 커서 (약점 3, 14, 15)

지금은 "직전 2턴 미확정 + 이번 턴"을 큐에 넣는다(`src/ts/process/index.svelte.ts:3803`). 이것을 "가장 오래된 미확정 턴부터 순서대로"로 바꾼다.

- 규칙: 위키는 이야기 순서대로만 갱신한다. 턴 K가 확정되지 않으면 K보다 뒤의 턴은 분석하지 않고 기다린다. 그러면 늦은 재시도가 최신 상태를 덮는 일이 원천적으로 사라지고, 과거 턴 표시나 현재 상태 보호 같은 예외 처리가 필요 없다.
- 커서는 따로 저장하지 않는다. 메시지의 기존 확정 표시(`risubardMemoryConfirmed`)에서 "첫 미확정 assistant 턴"을 찾으면 된다. 자동 확정을 처음 켠 채팅은 지금처럼 현재 경계부터 시작한다(과거 소급 금지 계약 유지).
- 처리 트리거: 응답이 성공할 때마다 커서부터 최대 K턴(기본 4)을 순서대로 처리한다. 밀린 턴이 많아도 한 번에 폭주하지 않고, 몇 번의 응답에 걸쳐 따라잡는다.
- 막힘 처리: 같은 턴이 결정적 오류(A의 상한 부족, 구조 검증 실패 반복)로 실패하면 도크 상단에 "밀린 턴 3개, 턴 1234에서 멈춤: 이유"를 띄운다. 버튼은 "다시 시도", "설정 열기", "이 턴 건너뛰기" 세 가지다. 건너뛴 턴은 확정 표시와 함께 영수증에 "사용자가 건너뜀"을 남긴다. 일시 오류(429, 네트워크)는 다음 응답 때 자동으로 다시 시도한다.
- 재실행 기록: 입력 해시(`risubard-memory-analysis.ts:1157`)에서 `sourceMessageOrder`를 뺀다. 같은 턴을 다시 돌릴 때 이미 반영한 문서를 건너뛰는 장치가 실제로 작동한다.
- 분석 시간 제한(`memoryAnalysisClient.ts:106`, 10분)을 없앤다. 취소는 기존 취소 신호로만 한다.
- 대상 한도를 넘는 정본 후보(약점 15)는 버리지 않고 영수증에 "다음으로 미룸"으로 남긴다. 다음 턴 분석 입력에 "미룬 후보" 목록으로 다시 넣는다.
- 다중 탭과 기기(약점 14): 서버에 채팅별 분석 임대를 둔다. 분석 시작 때 임대를 받고, 다른 탭은 임대가 풀릴 때까지 기다린다. 임대는 프로세스 메모리에만 두고 시간 제한 없이 작업 종료나 연결 종료로 풀린다.

공식 계약 영향: `context_pipeline_architecture.md`와 `markdown_narrative_wiki.md`의 확정 절에 "순서 보장과 밀린 턴 처리"를 추가한다.

## 단계 2. 정본을 항목 단위로 편집하기

### C. 항목 단위 편집 (약점 2, 6, 13)

지금 정본 갱신은 "바뀐 절의 전체 본문"을 받는다. 모델이 항목을 빠뜨리면 그대로 사라진다. 이를 다음처럼 바꾼다.

**모델에게 주는 것**: 대상 문서의 각 목록형 절을 번호 붙은 항목으로 준다(카드 정리가 이미 쓰는 `splitSectionUnits` 재사용).

**모델이 돌려주는 것**: 절마다 `operation`을 하나 고른다.

```json
{
  "heading": "지식과 비밀",
  "operation": "edit",
  "content": "",
  "add": ["새 항목"],
  "replace": [{ "index": 3, "text": "고친 항목" }],
  "remove": [{ "index": 7, "reason": "superseded", "into": null }]
}
```

- `edit`: 기존 절의 항목 편집. 언급하지 않은 항목은 그대로 남는다.
- `upsert`: 절 전체 교체. 현재 상태 절과 새 절에만 허용한다. 현재 상태는 원래 "지금 스냅샷"이라 교체가 맞다.
- `delete`: 절 삭제. 그 절의 모든 항목을 `remove`로 설명할 수 있을 때만 받아들인다.
- `remove.reason`: `superseded`(이번 턴 상태 변화로 낡음), `merged`(`into`가 가리키는 add 또는 replace 항목에 합침), `corrected`(원문이 틀렸다고 정정). 이유가 없거나 `into`가 잘못되면 그 항목은 남긴다.
- 지워진 항목에 있던 `[[링크]]`가 결과 어디에도 없으면 항목을 되살린다(정리 경로의 기존 규칙).

**모델이 규칙을 어기면**: 목록형 절에 `upsert`를 보내면 프로그램이 옛 항목과 새 본문을 대조한다. 새 본문에 근거가 없는 옛 항목(정리 경로의 `coverSupportsUnit` 기준)은 되살리고 영수증에 "보존: 3항목"을 남긴다. 즉 어떤 공급자나 개인 프리셋에서도 기본값이 보존이다.

**한 엔진으로 합치기**: 카드 정리(`risubard-canonical-maintenance.ts`)는 이 엔진의 "합치기 위주 편집"이 된다. 같은 적용 코드와 검증을 쓴다. 그 김에 다음을 고친다.
- 128개를 넘는 절은 128개씩 나눠 정리한다(약점 6).
- 정리 대상을 캐릭터만이 아니라 모든 정본 유형으로 넓힌다. 유형별 지시만 다르게 준다.
- "줄일 항목 없음"이 나와도 기준선을 자료별 상한 위로 올리지 않는다. 상한을 넘은 카드는 새 출처 8개마다 다시 시도한다(지금 오류 때 쓰는 방식).

**출력이 줄어드는 효과**: 바뀐 항목만 돌려주므로 출력 토큰이 줄고, 긴 절을 통째로 다시 쓰다 끊기는 일도 줄어든다.

**로어 참고 범위 좁히기 (약점 13)**: 로어 지시(`risubard-memory-analysis.ts:475`)가 채울 수 있는 것을 성별, 나이, 외모, 종족 같은 잘 바뀌지 않는 정체성으로 좁힌다. 관계, 역할, 지식은 로어로 채우지 않는다. "기존 정본에 기록된 이야기 사실이 로어보다 우선"을 넣는다. 위키 리부트에서는 로어를 현재 변수로 평가한다는 점을 지시에 밝히고, 같은 정체성 범위로만 쓴다.

공식 계약 영향: `markdown_narrative_wiki.md`의 "모델은 바뀐 H3 절의 전체 본문만 반환" 계약을 "목록형 절은 항목 편집, 현재 상태와 새 절은 전체 교체"로 고친다. 기존 문서와 개인 프리셋은 그대로 읽힌다(이관 없음).

## 단계 3. 시간 순번과 근거 규칙

### D. 사건 순번과 항목 순번 (약점 5, 7, 10, 12)

**사건 순번**: 사건을 처음 저장할 때 frontmatter에 `sequence`를 넣는다. 값은 작업공간의 기존 최댓값 + 1이다. 재분석과 추가 분석은 기존 값을 유지한다. B 덕분에 저장 순서가 곧 이야기 순서다. 위키 리부트는 순서대로 다시 매기고, 위키 승계는 값을 이어받는다. 순번이 없는 기존 사건은 지금처럼 메시지 순서로 계산하고, 처음 순번을 새로 쓸 때 메시지 순서대로 한꺼번에 채운다.

순번 하나로 다음이 풀린다.
- 모든 사건 자료에 "#1234, 현재 #5000"을 붙인다. 지금은 최근 48턴에만 붙는다(`risubard-inquiry-timeline.ts`). 분석 inquiry도 같은 표시를 받는다.
- 사건 lane은 점수로 고른 뒤 순번순으로 다시 늘어놓는다. 모델은 선후를 추측하지 않고 읽는다.
- 사건 제목 중복(약점 10): 저장할 때 같은 제목의 활성 사건이 있으면 제목 끝에 ` #1234`를 붙인다. 링크가 끊기지 않는다. 기존 중복은 건강도 진단에 보인다.
- 아크 체크포인트(약점 12): 표식을 사건 ID 대신 순번으로 쓴다(`<!-- risubard-story-arc-checkpoint: #1234 -->`). 그 사건이 지워져도 "1234보다 뒤의 사건"은 정의된다. 표식이 없어진 문서는 링크된 사건 중 가장 큰 순번으로 되살리고 경고한다. 기존 ID 표식은 읽을 때 순번으로 바꾼다.

**항목 순번**: C의 엔진이 정본 항목을 추가하거나 고칠 때 끝에 ` (#1234)`를 붙인다. 합친 항목은 가장 큰 순번을 갖는다. 모델이 쓴 순번 표식은 지우고 프로그램이 다시 붙인다. 이것이 "사실별 시점"이다. 출처 ID 목록(최근 96개)을 늘리지 않고도, 카드의 각 문장이 언제 기록됐는지 알 수 있다. 사람에게도 보이고 Obsidian에서도 그대로 읽힌다.

**아크 장 나누기 (약점 7)**: 살아 있는 아크 문서가 아크 수 상한에 닿으면 프로그램이 그 문서를 "스토리 아크 플롯 1장"으로 이름을 바꿔 고정하고(이후 다시 쓰지 않음), 새 아크 문서는 이전 장 링크 한 줄로 시작한다. 모델 호출이 늘지 않고, 닫힌 장은 다시 요약되지 않는다. 아크 행 적중 경로는 장 문서도 같은 예약 제목 계열로 인식한다.

작중 날짜(`storyTime`)는 공식 계약대로 둔다. 선후와 경과 턴은 순번이 맡고, 날짜는 원문에 명시된 경우의 보조 정보로 남긴다.

### E. 근거 규칙 다시 쓰기 (약점 4)

`narrativeContext.ts:62`의 규칙을 다음 뜻으로 바꾼다(실제 문구는 영어).

1. 자료가 서로 다르면 최근 대화 > 과거 원문 > 사건 > 정본 > 아크 플롯 순으로 따른다.
2. 정본 문장 끝의 `(#N)`은 기록된 시점이다. 같은 대상에 대해 순번이 큰 쪽이 더 최근이다.
3. 이야기에서 바뀐 사실은 위키를 따르고, 위키에 없는 설정은 로어북을 따른다.
4. 근거가 정하지 않은 세부는 지어내지 말고 모른다고 둔다.

자료마다 앞에 종류 표시(`[원문]`, `[사건 #1234]`, `[정본]`, `[아크]`)를 붙여 규칙이 실제로 적용될 수 있게 한다. 의도 판정 정규식(`risubard-markdown-inquiry.ts:716-745`)에 중국어 어휘를 넣는다.

### F. 비용을 턴 수에서 떼어 내기 (약점 8, 9, 11, 16)

- 분석 때 전체 위키를 받지 않는다(약점 9). 목차(`loadCatalog`)로 제목, 별칭, 순번, 해시를 보고, 본문은 후보, 재작성 대상, 직전 사건, 아크 대상 사건, 정리 표지 문서만 `readDocumentBodies`로 받는다.
- 링크 확장 이웃 정렬(약점 11): 앞 16개를 자르기 전에 이웃을 질의 점수, 순번 내림차순으로 정렬한다. 사건이 수천 개 붙은 인물 문서에서도 관련 높고 최근인 사건이 먼저 들어온다.
- 플러그인용 가상 기억(약점 8): `pluginBardWiki.ts`의 가상 기억에서 "# Recent conversation"을 뺀다. 플러그인은 채팅을 이미 읽으므로 중복이다. 가상 기억 주입을 끄는 설정을 둔다. 사건 출처로 찾는 원문 회수는 `allBefore` 경계를 무시하게 한다(어휘 검색은 지금처럼 경계를 지킨다). 이것은 `inquiry_context_compiler.md` 계약 변경이라 승인이 필요하다.
- 같은 인물 의심(약점 16): 건강도 진단에 "제목이나 별칭이 다른 문서의 별칭과 한 글자 차이" 같은 의심 쌍을 띄우고 COMBINE 템플릿으로 연결한다. 자동 병합은 하지 않는다.
- 기록 폴더(`.risubard-history`)를 없앤다(사용자 결정 2026-10-26). 앱 어디에서도 읽지 않는 쓰기 전용 사본이고, 되돌리기는 세이브 슬롯이 맡는다. 새로 쓰지 않고, 채팅 복제, 위키 승계, 세이브 사본에서도 뺀다. 기존 폴더는 구형 `.risubard-snapshots`를 지우는 기존 정리 루틴(`cleanupLegacySnapshots`)과 같은 방식으로 작업공간을 열 때 지운다. C의 보존 기본값이 들어가면 자동 갱신 실수를 기록 폴더로 되살릴 필요도 줄어든다.

## 검증 계획 (모델 비용 거의 없음)

**정답 분석기 테스트 (무료)**: 분석 러너의 `analyze` 주입점에 정답 장부에서 만든 JSON을 돌려주는 가짜 모델을 넣고, 코드로 만든 합성 장편을 실제 저장과 검색 경로로 돌린다. 사람이 플레이하거나 모델을 부르지 않으므로 턴 수는 비용이 아니라 실행 시간(수 분)만 늘린다. 기존 `pnpm bench:wiki-scale`과 같은 300, 1,000턴으로 돌리고, 사건 제목 중복과 이웃 16개 제한처럼 사건이 수천 개일 때만 드러나는 항목만 3,000턴에서 한 번 확인한다. 단계마다 다음을 회귀 테스트로 고정한다.
- 단계 1: 긴 응답과 큰 문서에서 잘림 0건, 넘치면 명시적 실패. 실패 턴 주입 시 순서대로 따라잡고, 결정적 실패는 멈춤 표시.
- 단계 2: 가짜 모델이 항목을 빠뜨리거나 절을 통째로 바꿔도 항목이 남는다. 이유 있는 지우기만 반영된다.
- 단계 3: 3,000턴 모든 사건 자료에 순번 표시, 체크포인트 사건 삭제 뒤에도 아크 갱신 계속, 중복 제목 링크가 모두 해석된다.
- 단계 4: 분석 한 번의 전송량이 100턴과 3,000턴에서 비슷하다(`pnpm bench:wiki-scale`에 항목 추가).

**10턴 실사용 감시 (저가 모델 수십 회 호출)**: 단계 1이 들어간 뒤 스크래치 데이터 루트에서 합성 봇으로 10턴을 진행한다. 응답을 일부러 3,000자 이상으로 길게 하고, 로어북 하나와 관계가 바뀌는 장면 둘을 넣는다. 매 턴 영수증, 요청 로그의 입력 토큰, 정본 파일 차이를 기록한다.
- 10턴으로 확인되는 것: 잘림과 실패 표시(A), 순서 처리(B), 항목 보존(C), 순번과 근거 규칙 적용(D, E), 로어 범위.
- 10턴으로 확인되지 않는 것: 수천 턴 누적 표류와 규모 문제. 이것은 위 정답 분석기 테스트가 맡는다.

지금 코드로 10턴 감시를 먼저 하면, 잘림과 항목 손실을 볼 계측이 없어서 요청 로그의 토큰 수로 추정하는 정도만 가능하다. 단계 1 뒤에 하는 편이 얻는 것이 많다.

## 하지 않는 것

- 별도 그래프, JSON 색인, 사실 데이터베이스를 만들지 않는다. 순번과 표식은 Markdown과 frontmatter 안에 있다.
- 정본 문서 크기에 글자 수 제한을 다시 두지 않는다. 크기는 정리와 항목 편집으로 다룬다.
- 저장, 동기화, 모델 대기에 시간 제한을 두지 않는다.
- 응답 경로에 모델 호출을 늘리지 않는다. 늘어나는 호출은 밀린 턴 따라잡기뿐이며, 원래 했어야 할 분석이다.
