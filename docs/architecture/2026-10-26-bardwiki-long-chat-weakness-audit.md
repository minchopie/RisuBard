- 범위: `RisuBard-public` 현재 체크아웃(0.9.83 릴리스 이후)의 바드위키 기억 파이프라인. 턴 분석, 사건 문서, 캐릭터 정본(현재 상태 카드), 아크 플롯, 정본 정리, 회수, 프롬프트 주입, 0.9.83 로어북 참고.

- 측정 하나: 자동 분석 첫 호출의 시스템 지시문 크기를 기본 프리셋 기준으로 `cl100k_base`로 셌다(아래 1번). 나머지 수치는 코드의 상수와 산술이다.

## 결론

코드만으로는 "초장기 채팅을 완벽하게 해낸다"를 보일 수 없고, 지금 코드에는 턴 수가 늘수록 조용히 기억을 잃거나 틀리게 만드는 경로가 여럿 남아 있다. 가장 큰 세 가지는 다음과 같다.

1. 기본 설정(`AI 분석 토큰 상한` 8,192)에서 분석 시스템 지시문만 약 4,965토큰이라, 확정 턴 원문이나 기존 정본 본문이 경고 없이 잘려 모델에 들어간다.
2. 일반 턴의 정본 절 교체는 모델이 돌려준 본문을 구조만 확인하고 저장한다. 항목이 빠져도 코드가 알지 못한다.
3. 분석에 실패한 턴은 직전 2턴 범위에서만 자동 재시도되고, 늦게 재시도되면 오래된 상태가 최신 정본을 덮을 수 있다.

37만 토큰 테스터 제보는 다른 장기 기억 플러그인과 함께 쓴 결과라 바드위키 단독 품질의 근거로 쓰기 어렵다. 플러그인 간섭 경로도 코드에 실제로 있다(8번). 1.0 판단에는 아래 벤치마크처럼 정답이 알려진 합성 장편으로 측정한 수치가 필요하다.

## 약점 목록 (심각한 순)

심각도 기준: 높음은 초장기 채팅에서 기본 설정으로도 조용히 일어날 가능성이 큰 기억 손실이나 왜곡, 중간은 특정 조건이나 규모에서 일어나는 것, 낮음은 영향이 작거나 사용자가 알아챌 수 있는 것.

### 1. [높음] 분석 입력이 상한을 넘으면 확정 원문과 기존 정본을 조용히 자른다

근거
- `src/ts/risubard/memoryAnalysisClient.ts:155-235` `fitAnalysisInput`: 상한을 넘으면 `existingNotes`를 1개까지 버린 뒤, `content`, `markdown`, `confirmedEvent` 키의 가장 긴 문자열을 25%씩 자른다. 역할(`role`)이 있는 메시지 본문은 뒤쪽을 남기고(`:224`), 정본 대상 `markdown`은 앞쪽을 남긴다. 잘랐다는 사실은 영수증이나 경고 어디에도 남지 않는다.
- 모든 분석 호출이 이 함수를 거친다(`memoryAnalysisClient.ts:1052`).
- 기본 상한 8,192(`src/ts/risubard/risuBardSettings.ts:9`). 기본 공식 프리셋에서 첫 호출 시스템 지시문(작성 계약 1,307 + 분석 가이드 2,181 + 사건 정책 272 + 통합 지시 304 + 정본 정책 865 등)이 약 4,965토큰이다(이번 측정). 로어 참고를 켜면 지시가 더 붙는다. 남는 입력 예산은 약 3,200토큰이다.
- 그 안에 줄일 수 없는 `completeCanonicalDocuments`(`completeText` 키, 상한의 1/4인 최대 2,048토큰, `risubard-memory-analysis.ts:1254-1268`), 로어 참고(기본 1,000토큰, 0.9.83 추가), 직전 사건 요약 1,200자, 확정 원문이 함께 들어간다.
- 정본 재작성 배치 분할은 시스템 지시문 크기를 빼지 않고, 한 대상이 상한을 넘어도 그대로 보낸다(`risubard-memory-analysis.ts:159-178`).

실패 시나리오
- 한국어 3,000자 안팎의 긴 응답이 이어지는 채팅. 첫 호출에서 확정 응답의 앞부분이 잘려 사건 요약과 상태 변화에서 장면 전반부가 빠진다. 영수증은 정상으로 보인다.
- 6,000자를 넘는 장소 문서나 조사 줄기 문서, 아크 플롯(최대 12,000자)을 갱신할 때 `markdown`의 뒷부분이 잘린 채 모델에 간다. 모델이 잘린 절을 `upsert`로 돌려주면 보지 못한 뒷부분 항목이 저장본에서 사라진다. 2026-09-29 점검에서 BARDCHAT에서 고친 "앞부분만 남기고 전체 교체" 결함과 같은 종류가 자동 분석 경로에 남아 있다.

고칠 방향
- 확정 원문과 정본 대상 본문은 절대 자르지 않는다. 넘치면 명시적으로 실패시키거나 턴을 나눠 분석하고, 영수증에 이유를 남긴다.
- 배치 분할과 예산 계산에 시스템 지시문 토큰을 포함한다. 기본 상한을 지시문 크기에 맞게 올리거나 지시문을 줄인다.
- 정본 대상이 들어가지 않으면 관련 절만 보내고, 프로그램이 "입력에 전부 들어간 절만 upsert 허용"을 검사한다.
- 잘림이 생기면 영수증 경고와 활동 기록에 남겨 벤치마크와 테스터 제보에서 보이게 한다.

### 2. [높음] 일반 턴의 정본 절 교체에서 내용 보존을 코드가 확인하지 않는다 (알려진 1번)

근거
- `server/node/risubard-markdown-section-patch.ts:237-307` `applyCanonicalSectionPatches`는 제목 구조, 중복 절, 빈 문서만 검사한다. `delete`로 절 전체를 지우는 것도 허용한다(`:256,278`).
- 정본 재작성 지시는 "바뀐 절의 전체 교체 본문"을 요구한다(`risubard-memory-analysis.ts:1734-1767`). 기존 항목을 빠짐없이 다시 쓰는 일은 모델에 맡겨진다.
- 항목별 처분 검사(`kept`, `merged`, `moved`, `covered`)와 링크 보존 복원은 카드 정리 경로에만 있다(`risubard-canonical-maintenance.ts:224-299`). 일반 턴 저장에는 없다.

실패 시나리오
- `지식과 비밀` 절에 25개 항목이 있는 인물을 새 사실 하나 때문에 갱신한다. 모델이 22개만 돌려주면 3개가 사라지고 경고가 없다. 주연 인물은 수천 턴 동안 수백 번 이 교체를 거치므로 손실이 누적된다. 복구 수단은 `.risubard-history`의 이전 판뿐이고, 무엇이 빠졌는지 알려 주지 않는다.

고칠 방향
- 목록형 절의 upsert에 정리 경로와 같은 단위 대조를 적용한다. 최소한 링크 보존 검사, 항목 수 급감 감지, 사라진 항목 목록을 영수증에 남긴다.
- 사라진 항목이 상태 변화로 설명되지 않으면 원문 항목을 되살린다.
- 절 `delete`는 해당 절을 대체하는 근거가 있을 때만 허용한다.

### 3. [높음] 실패한 턴은 직전 2턴 안에서만 재시도되고, 늦은 재시도가 최신 상태를 덮을 수 있다

근거
- 자동 재시도 범위가 대상 턴 앞의 assistant 턴 2개다(`index.svelte.ts:3803-3809`, `memoryAnalysisClient.ts:743-769`). 그보다 오래된 미확정 턴을 다시 처리하는 자동 경로나 일괄 처리 버튼이 없다. 메시지별 수동 확정 버튼만 있다.
- 재시도된 옛 턴은 `historicalReanalysis`로 표시되지 않아, 최신 현재 상태 절을 보호하는 처리(`risubard-memory-analysis.ts:2008-2012`, 함수 `:137`)가 적용되지 않는다.
- 같은 입력 재실행에서 이미 반영한 문서를 건너뛰는 기록은 입력 해시가 같을 때만 쓰인다(`:1157-1162`). 해시에 채팅 전체의 메시지 순서(`sourceMessageOrder`, `index.svelte.ts:407`)가 들어가므로, 새 메시지가 하나라도 생긴 뒤의 자동 재시도에서는 항상 다르다. 그래서 첫 시도에서 저장된 정본을 다시 갱신한다.
- 분석 전체에 10분 제한이 있다(`memoryAnalysisClient.ts:106`). 느린 사고형 모델이나 큰 위키에서 실패를 만든다. 저장과 모델 대기에 시간 제한을 두지 않는다는 프로젝트 원칙과도 어긋난다.

실패 시나리오
- 공급자 장애나 429로 세 턴 연속 실패하면 가장 오래된 턴은 창 밖으로 밀려 영원히 위키에 들어가지 않는다. 사용자는 메시지별 표시를 하나씩 확인해야만 안다.
- 턴 N이 실패하고 N+1이 성공한 뒤, 다음 기회에 N이 성공하면 N 시점의 "현재 상태"가 N+1 이후 상태를 덮는다. 예: N에서 "부상", N+1에서 "회복". 늦은 N 재시도가 다시 "부상"으로 되돌린다.

고칠 방향
- 채팅별 분석 커서를 저장해 가장 오래된 미확정 턴부터 순서대로 처리하고, 앞 턴이 끝나기 전에는 뒤 턴 정본 갱신을 미루거나, 늦은 재시도를 과거 재분석으로 표시한다.
- 입력 해시에서 `sourceMessageOrder`를 빼고 대상 메시지와 설정만 넣는다.
- 미확정 턴 수를 도크에 표시하고 "밀린 턴 분석" 일괄 실행을 제공한다.
- 분석 시간 제한을 없앤다.

### 4. [높음] 응답 근거 규칙에 충돌 우선순위가 없고, 로어북과 위키가 다르면 기준이 없다 (알려진 4번)

근거
- `src/ts/risubard/narrativeContext.ts:62-67`: 첫 줄이 모든 검색 자료를 "authoritative evidence"로 부른다. 정본과 아크 플롯도 포함된다. 과거 세부는 원문과 사건을, 현재는 정본을 "prefer"하라는 선호만 있고, 서로 다를 때 무엇을 따를지 정하지 않는다.
- 로어북 항목은 프롬프트 앞쪽 정적 위치에, 위키 자료는 최신 사용자 메시지 앞에 들어간다(`index.svelte.ts:2980`). 로어북과 위키 사이 우선순위 규칙은 없다. 분석 경로에는 "원문과 로어가 다르면 원문"만 있다(`risubard-memory-analysis.ts:475-480`).
- 일반 진행 입력에서는 정본 앵커 최대 4개가 먼저 목표 예산을 차지하고 사건은 남는 예산에 들어간다(`risubard-markdown-inquiry.ts:897-920`). 사건 lane과 현재 상태 lane은 마지막 사용자 메시지의 정규식으로 정한다(`:716-745`). 정규식에 중국어가 없어, 简体中文과 繁體中文 위키 사용자에게는 의도 판정이 작동하지 않는다.

실패 시나리오
- 원작 봇에서 2,000턴 동안 이야기가 갈라져 인물 A가 길드를 떠났다. 로어북은 여전히 "A는 길드장"이고 위키 정본은 "A는 길드를 떠났다"다. 모델은 두 자료를 같은 무게로 받아 섞어 쓴다.
- 정본 관계 절의 압축된 문장과 회수된 사건 원문의 세부가 다를 때, 모델이 정본 쪽을 따라 원문과 다른 세부를 말한다.

고칠 방향
- 근거 규칙에 명시적 순서를 넣는다: 최근 원문 > 회수 원문 > 사건 > 정본 > 아크 플롯. 이야기에서 바뀐 사실은 로어북보다 위키를 따르고, 바뀌지 않은 설정은 로어북을 따른다.
- 자료마다 종류와 시점 표시를 붙여 모델이 충돌을 판단할 수 있게 한다.
- 의도 판정에 중국어를 넣거나 언어에 덜 의존하는 방식으로 바꾼다.

### 8. [중간] 다른 장기 기억 플러그인과의 간섭

근거
- v3 플러그인이 채팅을 읽으면 바드위키가 `hypaV3Data.summaries`, `hypaV2Data.mainChunks`, `supaMemoryData`에 가상 기억을 넣어 준다(`src/ts/plugins/apiV3/v3.svelte.ts:652-676`, `src/ts/risubard/pluginBardWiki.ts:123-170`). 그 안에는 검색 자료와 "# Recent conversation" 최근 대화가 함께 들어간다(`pluginBardWiki.ts:221-246`). 이 경로의 검색은 timeline, 원문 회수, 인물 힌트 없이 마지막 사용자 메시지로만 한다(`:265-285`).
- 과거 원문 회수와 timeline은 마지막 `disabled: 'allBefore'` 이전 메시지를 모두 제외한다(`src/ts/risubard/historicalSourceRecall.ts:93-97,215-219`).
- 분석은 메시지 본문을 그대로 읽는다. 다른 플러그인이 메시지를 고치거나 요약 메시지를 끼워 넣으면 그대로 사건이 된다.

실패 시나리오
- 기억 플러그인이 `hypaV3Data.summaries`를 읽어 주입하면 바드위키 자료와 최근 대화가 다른 선택 기준으로 한 번 더 들어간다. 같은 사실의 두 판본이 들어가고, 시점 표시는 한쪽에만 있다.
- 플러그인이 자체 요약을 주입하면 바드위키 정본과 다른 요약이 우선순위 없이 함께 들어간다. "기억이 사소하게 어긋난다"는 증상과 맞는다.
- 문맥을 줄이려고 `allBefore`를 쓰는 플러그인이 있으면 사건 출처 원문 회수가 전부 끊긴다.

고칠 방향
- 기억 계열 플러그인이 켜져 있으면 도크에 알리고, 플러그인용 가상 기억에서 최근 대화를 빼거나 끌 수 있게 한다.
- 원문 회수는 `allBefore`와 무관하게 사건 출처 ID로 찾게 한다. 프롬프트 제외와 기억 근거 제외를 구분한다.
- 테스터 검증 안내에 "다른 기억 플러그인을 끄고 재현"을 넣는다.

### 9. [중간] 매 턴 전체 위키 본문을 내려받고, 기록 폴더는 줄지 않는다

근거
- 분석마다 `/api/risubard/memory/view`로 모든 문서 본문을 받는다(`memoryAnalysisClient.ts:948-963`, 서버 `risubard-markdown-wiki.ts:2216`, 폴더 재확인 포함 `:906-922`). 2026-10-08 규모 계약("누적 턴 수에 비례하면 안 된다")과 어긋난다. 사건 1.4KB, 3,000턴이면 턴마다 수 MB의 JSON이다. 원격이나 모바일에서 3번의 시간 제한 실패를 부른다.

고칠 방향
- 분석은 본문 없는 목차와 필요한 문서 본문만 받는다(`loadCatalog`, `readDocumentBodies`가 이미 있음).
- 기록은 문서별 최근 N판 또는 크기 상한으로 정리한다. 세이브 슬롯은 해시 저장이라 영향이 작다.

### 13. [중간] 로어북 참고를 현재 변수 값으로 평가해 과거 턴에 넣는다

- 건강도 진단에 "같은 인물 의심" 항목을 추가하고 COMBINE을 제안한다.

## 품질 벤치마크 설계안

### 목표

턴 수가 늘어도 다음이 유지되는지 체크포인트마다 숫자로 본다.

- 근거 포함률: 정답에 필요한 원문이나 문서가 최종 모델 입력에 들어갔는가.
- 답 정확도: 고정 사실, 최신 값, 특정 시점의 값, 순서, 인물별 지식 경계.
- 지어낸 기억: 일어나지 않은 일, 거짓 단서, 틀린 전제 질문에 "모른다"나 정정으로 답하는가.
- 위키 표류: 정답 장부의 사실이 위키에 남아 있고 최신인가. 위키에만 있고 장부에 없는 사실은 얼마나 되는가.
- 조용한 손실: 미확정 턴 수, 입력 잘림 횟수, 정본 항목 감소 수(1, 2, 3번 계측이 먼저 필요하다).
- 비용: 턴당 입력과 출력 토큰, 지연, 위키 크기. 체크포인트 사이에 늘지 않아야 한다.

2026-09-29 점검의 목표(이름이 있는 질문 96%, 바꿔 말한 질문 80%)와 LongMemEval의 분류(시간 추론, 지식 갱신, 여러 사건 결합, 답할 수 없는 질문)를 이어받는다.

### 합성 장편 생성기

시드가 있는 결정론적 세계 상태 기계가 턴마다 사실 계획을 만들고, 그 계획에서 사용자 메시지와 assistant 본문을 만든다. 정답 장부(JSON)를 함께 출력한다.

- 등장인물 12명, 장소 10곳, 물건 20개. 같은 장소와 비슷한 사건을 반복해 제목 중복과 검색 혼동을 일부러 만든다.
- 심는 사실 종류
  - 고정 사실: 초반에 한 번만 나오고 끝까지 바뀌지 않는다(출신지, 흉터의 원인).
  - 갱신 사실: 관계, 소유, 위치, 부상 상태가 여러 번 바뀐다. 최신 값과 "턴 T 무렵의 값"을 둘 다 묻는다.
  - 순서 사실: 비슷한 사건 두 개의 선후.
  - 지식 경계: 인물 X만 비밀을 알게 되는 턴. Y는 모른다.
  - 거짓 단서: 소문, 거짓말, 오해를 심고 몇 백 턴 뒤 정정한다.
  - 작중 날짜: 명시 날짜와 "며칠 뒤", 날짜 불명 구간을 섞어 날짜 연쇄 끊김을 재현한다.
  - 로어북 충돌: 합성 로어북에 원래 설정을 넣고 이야기에서 바꾼다.
  - 일어나지 않은 일: 질문에만 쓰는 반사실 목록.
- 본문 두 가지
  - 템플릿 본문: 무료, 결정론. 문장 틀과 바꿔 말하기 표현 풀로 만든다. 코드 경로 검증용.
  - 모델 본문: 턴별 사실 계획을 주고 저가 모델이 소설체로 쓴다. 심은 사실의 표면 문자열이 들어갔는지 코드가 검사하고, 빠지면 다시 쓴다. 한 번 만들어 픽스처로 저장하고 재사용한다. 공개 저장소에는 생성 스크립트와 시드만 두고 사용자 채팅은 쓰지 않는다.
- 응답 길이를 짧은 것(800자)과 긴 것(3,000자 이상) 두 벌로 만든다. 1번의 잘림은 긴 쪽에서만 드러난다.

### 체크포인트와 질문

- 체크포인트: 100, 300, 1,000, 3,000턴. 여유가 있으면 5,000턴.
- 각 체크포인트에서 위키 작업공간을 복사해 고정하고, 질문 60에서 100개를 던진다.
- 질문마다 정답 키(짧은 값이나 선택지), 필요한 근거(메시지 ID, 사건 ID), 분류를 둔다. 답은 `{ answer, unknown, evidence }` JSON으로 받아 대부분 코드로 채점하고, 자유 서술만 저가 판정 모델로 채점한다.

### 단계

| 단계 | 내용 | 모델 호출 | 무엇을 가려내나 |
| --- | --- | --- | --- |
| 0 | 정답 분석기로 위키를 만들고 회수만 잰다 | 없음 | 코드와 검색의 손실(10, 11, 4번의 lane, 5번의 시점 표시, 8번의 `allBefore`) |
| 0F | 정답 분석기에 결함을 주입한다(항목 누락, 실패 턴, 긴 입력) | 없음 | 2, 3, 1번 방어 장치가 손실을 잡는가 |
| 1 | 실제 분석 모델로 위키를 만들고 장부와 대조한다 | 분석 모델 | 모델과 파이프라인의 누적 표류, 지어낸 사실 |
| 2 | 실제 응답 모델로 질문에 답한다 | 응답 모델, 판정 모델 | 최종 답 정확도, 시간 순서, 지어낸 기억 |

0단계 정답 분석기는 `createMemoryAnalysisRunner`(`server/node/risubard-memory-analysis.ts:1074`)의 `analyze` 주입점에 장부에서 만든 스키마 JSON을 돌려주는 함수를 넣는다. 실제 저장, 제목, 링크, 아크 계획, 정리 판단, 원문 회수, inquiry가 그대로 돈다. 기존 서버 테스트 방식(`vitest.config.server.ts`)으로 실행한다.

2단계 비교 조건

- A: 바드위키(기본 설정).
- B: 전체 원문(모델 문맥이 허용하는 체크포인트까지만, 300턴 이하 권장).
- C: 최근 원문만(하한선).
- D: 바드위키와 가상 기억 플러그인(자체 요약 블록을 주입하는 테스트 플러그인)을 함께. 8번 간섭을 잰다.

### 기존 자원 재사용

- `pnpm bench:wiki-scale`(`server/node/risubard-wiki-scale.fixture.ts`, `risubard-wiki-scale.bench.test.ts`, `src/ts/risubard/wikiScale.bench.test.ts`): 시드 난수, 작업공간 경로, frontmatter 작성기, `RISUBARD_SCALE_TURNS` 크기 지정, 시간 측정 틀을 그대로 쓴다. 다만 이 픽스처는 무작위 문장을 미리 써 둔 위키라 정답이 없고 파이프라인을 거치지 않는다. 품질 측정에는 쓸 수 없고 성능 회귀 확인을 같은 실행에 붙이는 용도다.
- echo 모델(`src/ts/process/request/request.ts:1954-1955`): 모든 호출에 같은 문장을 돌려주므로 분석 JSON을 턴마다 다르게 만들 수 없다. 앱 단위 흐름(자동 확정 큐 순서, 생성 잠금, 실패 턴 재시도, 영수증 표시)을 비용 없이 확인하는 데만 쓴다. 앱 단위로 0단계를 돌리려면 장부 JSON을 돌려주는 로컬 OpenAI 호환 모의 서버를 분석 보조 모델로 지정하는 편이 낫다.

### 실제 모델이 필요한 부분과 비용 추정

아래 단가는 가정이다. 실행 전에 실제 공급자 가격으로 바꿔 계산한다.

- 가정 A(저가 flash급): 입력 100만 토큰당 0.30달러, 출력 2.50달러.
- 가정 B(중급): 입력 3달러, 출력 15달러.

| 항목 | 규모 | 토큰 추정 | 가정 A | 가정 B |
| --- | --- | --- | --- | --- |
| 모델 본문 생성(선택, 1회) | 3,000턴 | 출력 약 360만 | 약 9달러 | 약 54달러 |
| 1단계 분석 | 3,000턴, 턴당 입력 약 1.4만, 출력 약 2천(첫 호출, 정본 재작성 약 40%, 정리와 아크 포함) | 입력 약 4,200만, 출력 약 600만 | 약 28달러 | 약 216달러 |
| 2단계 A, C, D | 체크포인트 4개, 질문 80개, 호출당 입력 약 1만 | 입력 약 1,000만 | 약 3달러 | 약 30달러 |
| 2단계 B(전체 원문) | 300턴 체크포인트 하나, 질문 80개, 호출당 약 40만 | 입력 약 3,200만 | 약 10달러 | 약 96달러 |
| 판정 모델 | 자유 서술 1,000건 내외 | 입력 약 200만 | 1달러 미만 | 약 6달러 |
| 합계(본문 생성 포함) | | | 약 50달러 | 약 400달러 |

- 분석 시스템 지시문 약 5천 토큰은 매 호출 같으므로, 프롬프트 캐시를 쓰면 1단계 입력 비용이 크게 줄어든다.
- 시간: 한 채팅의 분석은 순서대로만 돈다. 턴당 20에서 40초면 3,000턴에 17에서 33시간이다. 시나리오 여러 개를 병렬로 돌린다.
- 0단계와 0F단계는 모델 비용이 없다. 1번에서 3번 약점을 고친 뒤 효과를 먼저 여기서 확인하고, 1단계와 2단계는 릴리스 후보마다 한 번 돌린다.

### 1.0 판단 기준 제안

3,000턴 체크포인트, 저가 분석 모델 기준으로 다음을 제안한다. 수치는 합의 전 제안이다.

- 이름이 있는 질문의 근거 포함률 96% 이상, 바꿔 말한 질문 80% 이상(2026-09-29 목표).
- 최신 값 정확도 90% 이상, 옛 값으로 답한 비율 5% 이하.
- 순서 질문 정확도 85% 이상.
- 답할 수 없는 질문과 틀린 전제 질문에서 지어낸 답 5% 이하.
- 미확정 턴 0개, 또는 남은 미확정 턴이 모두 사용자에게 보임. 입력 잘림 0건.
- 턴당 분석 토큰과 응답 입력 토큰이 100턴 대비 3,000턴에서 20% 넘게 늘지 않음.

## 이번 점검에서 확인하지 못한 것

- 실제 모델 출력으로 2번과 3번의 손실이 얼마나 자주 일어나는지는 재지 않았다. 코드상 막는 장치가 없다는 판정이다.
- 1번은 시스템 지시문 크기를 실제로 쟀고, 나머지 입력 크기는 상수와 산술로 추정했다. 실제 잘림 빈도는 계측을 추가해야 안다.
- 개인 프리셋, 다른 언어 프리셋, 임베딩을 켠 경로의 지시문 크기와 회수 품질은 따로 재지 않았다.
- 테스터의 37만 토큰 채팅은 보지 않았다. 증상의 원인이 바드위키인지 함께 켠 플러그인인지는 판단하지 않았다.
