## 실사용 중 발견한 오류와 수정

후보31은 최초6자리 등록과 파일 전달은 성공했지만, 현재 선택하지 않은 캐릭터로 가져올 때 채팅 본문을 저장하지 않고 stub/적용 표식만 저장했다. 이어지는 해시 검증이 실패해 복구 보류 화면으로 돌아왔다.

원인은 선택된 캐릭터 중심의 dirty tracking이다. `requestImmediateSave`가 가져오기 대상의 정확한 `[characterId, chatId]` 쌍을 동기적으로 등록하도록 하고, `receiveTransfer`가 추가한 채팅 쌍을 전달하게 했다. 본문 업로드 → 메타데이터 → canonical flush → 최종 확인 순서를 재사용한다. 제품 수정은 `src/ts/globalApi.svelte.ts`, `src/ts/playTransfer.ts` 두 파일이다.

실패한 합성 채팅은 원본 수신 파일/작업 기록과 앱 백업을 먼저 보존했다. 수신 페르소나 연결을 포함한 원래 적용 예정 내용의 SHA-256이 작업 기록과 일치함을 확인한 뒤, 기존 앱 저장 API와 서버 최종 검증으로 해당 합성 채팅만 복구했다. 개인 채팅의 직접 DB 수정이나 초기화를 하지 않았다. 이는 수동 복구 기록이며 자동 복구 성공 시험으로 계산하지 않는다.

자체 검사: 관련 클라이언트23개, 실제 바이너리 채팅 업로드/flush/서버 재시작/finish의 새 캐릭터·기존 캐릭터2개, 타입0오류/기존8경고, 웹 및 두 Android 빌드 통과. 실제 Opus 코드 검수2차는 범위 내 확정 차단 결함을 찾지 않았다. 지적한 JSON 대신 실제 msgpack 업로드 시험을 보강했고2개가 통과했다. 최종 제품 두 파일은 검수 입력 해시와 동일하다. 최종 실기기 근거 검수도 `claude-opus-5-5`/xhigh, 종료0/is_error=false로 완료했으며 지정 범위의 확정 차단 결함 없음이다. 추가 권고한 기존/수신 채팅 ID가 서로 다르다는 단언을 시험에 넣고2개를 다시 통과했다. 제품/APK 바이트는 바뀌지 않았다. 원문: [OPUS-DEVICE-QA-20261017.md](OPUS-DEVICE-QA-20261017.md).

검수 한계: 이미 실행 중인 다른 자동 저장과 수신 적용이 극히 짧게 겹친 뒤 강제 종료되는 경우는 전수 재현하지 않았다. 검수자가 제시한 기존 복구 보류 가능성을 해결 완료로 표시하지 않는다. 실패 수신 파일/저널은 보존하는 경로다.
