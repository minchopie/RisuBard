# RisuBard 구조와 MGE 로어 호환성 검토 — 2026-10-17

## 결론과 범위

현재 MGE 로어를 대폭 다시 쓰기 전에 **로어 선택 설정과 기억 처리의 연결을 바로잡아야 한다.** 기존 로어북 경로로 사용할 수 있지만, 설정만 복사하거나 Grimoire를 켜는 것으로 같은 실행 결과를 보장할 수 없다.

- **GOAL:** 공개 GitHub/온라인 자료와 실제 소스를 대조해 기존 USB 앱과 RisuBard의 차이를 확인하고 MGE 로어를 검토한다.
- **MUST:** 실측·코드 근거·추정을 구분하고 실제 Opus 5.5 Extra(xhigh)와 교차 검수한다. 사용자 결정에 따라 로컬 AI 작업은 종료한다.
- **KEEP:** 로어 원문·키·ID·Lua·모듈·플러그인·기존 대화와 사용자 설정. 검토만으로 로어 삭제/축약, 앱 초기화, 모델 삭제를 수행하지 않는다.
- **VERIFY:** 현재 원격 커밋, 배포 카드/미배포 후보의 파일 해시와 구조, 실제 로어 선택 함수를 이용한 합성 입력 비교, 읽기 전용 공동 검수.

이 문서는 **구조·호환성 검토**다. 749개 로어의 사실·문장 전수 교정, 실제 유료 API 응답, 실기기의 현재 설정 재조회나 수정은 수행하지 않았다.

## 확인한 문제와 조건

### A. 캐릭터 로어 설정 부재에 따른 예산 부족과 기본 재귀 탐색

이전 작업의 태블릿 일반판 저장본은 캐릭터 `loreSettings`가 없고 `bardLore.mode='legacy'`이다. 설정 초기화 직전 전역 예산8,000이 초기화 뒤 기본값800으로 바뀌었다. 캐릭터별 설정 부재는 패치 전부터 있었으므로 이 초기화가 지웠다고 단정하지 않는다. 전역값 초기화는 이번에 확인한 누락을 악화시켰다.

실제 `loadLoreBookV3Prompt`에 저장본의 로어/설정을 넣고 합성 입력 `산크타벨의 거리를 둘러본다.`를 사용했다. 800예산에서는 전체2개, 그중 상시1개만 선택되었다. **상시18개가 빠졌다.** 메모리 안에서 카드 지정 설정64,000/스캔4/재귀꺼짐을 적용한 대조군은 상시19개를 모두 선택했다. 최초 대조는 예산·스캔·재귀를 함께 바꿨으므로 선택 목록의 모든 차이를 예산만의 효과로 해석하지 않는다. Opus 지적에 따라 각 변수를 분리한 후속 시험을 추가했다.

변수 분리 시험은 같은 합성 입력과 로어에서 예산3종×재귀2종×스캔2종, 총12조합으로 실행했다. 스캔4/5의 결과는 이 짧은 입력에서는 같았다.

| 예산 | 재귀 | 선택된 전체 / 상시19개 중 | 입력에서 언급한 산크타벨 지역 |
|---:|---|---:|---|
| 800 | 켜짐 | 2 / 1 | 누락 |
| 800 | 꺼짐 | 2 / 2 | 누락 |
| 8,000 | 켜짐 또는 꺼짐 | 13 / 13 | 누락 |
| 64,000 | 켜짐 | 66 / 14 | 누락 |
| 64,000 | 꺼짐 | 20 / 19 | 선택 |

예산만64,000으로 올리고 재귀를 켜 두어도 충분하지 않았다. 상시 여부가 예산 탈락을 막아 주지는 않으며, 소스는 재귀로 선택 후보를 늘린 뒤 우선순위순 예산 필터를 적용한다. 각 항목의 탈락 직전 토큰/사유를 별도 기록하지 않았으므로 이 구체적인 탈락 경위는 소스와 행렬을 결합한 해석이다. 초기800 상태에서 선택된Ares는 재귀를 끄면 선택되지 않는다. 앞선8,000 상태도 이 시험에서는 상시6개와 직접 언급한 산크타벨이 빠졌으므로 초기화 전부터 설정 문제가 있었고,800초기화가 이를 악화시켰다고 구분한다.

실제 런타임은 전역 예산/깊이를 읽지만 재귀는 캐릭터값이 없으면true이고 매칭도 캐릭터값에서 정한다. 전역 재귀/매칭 필드를 누락해 생긴 하니스 오류는 아니다. 행렬에서는 매칭값/최대재귀를 생략했고 함수 기본값은 각각partial/0이다(`lorebookMatching.ts:16–23`, `lorebook.svelte.ts:203`). 따라서 배포 카드와 이 두 유효값은 같지만 행렬의 설정 객체 전체가 카드 설정 객체와 동일한 것은 아니다. 별도 카드 지정 설정 대조군에서도 상시19개/산크타벨 포함을 확인했다.

앞선 설정 이전 검수는 요청한 기본값/이전값의 저장과 재시작 유지를 확인한 것이며, MGE 필수 문맥의 충분성을 검증하지 못했다. 이전의 "설정 저장 검증 통과"를 "카드 실플레이 호환 검증 통과"로 확대해서는 안 된다. 현재 기기에서 사용자가 설정을 더 바꿨는지는 이번에 조회하지 않았다.

최소 수정 후보는 **MGE 캐릭터에 배포 카드의 로어 설정을 적용**하는 것이다. 기기에서 이 설정이 있었다는 증거는 없으므로 기기 상태의 ‘복원’으로 부르지 않는다. 전역 설정 전체 복원이나 캐릭터 재가져오기·채팅 초기화를 묶어서 실행하지 않는다. 다른 모드로 전환했거나 이후 사용자 변경이 있으면 적용 전에 현재 상태를 대조해야 한다.

실제 공개 가져오기 함수와 트랜잭션 경로를 사용한 추가 검사에서 배포1.2.27/후보1.3.0의 설정과749항목이 저장 요청 시점까지 유지됐다. CHARX 압축 해제·에셋·UI·저장 장치는 모의 처리했으므로 실기기의 영속 저장이나 업데이트 경로 전체를 검증한 것은 아니다. 설정 부재가 시작된 이전 경로는 아직 특정하지 못했다. 전역값 전후 비교는 값 대신 변경 키 목록을 별도로 남겼으며 비밀정보는 출력하지 않았다.

근거: `src/ts/process/lorebook.svelte.ts:95`, `:195`, `:731`, `src/ts/storage/database.svelte.ts:166`, 비공개 저장본의 안전한 필드 비교 `snapshot-settings.json`.

### B. Grimoire 단순 전환은 MGE의 상시/정규식 계약과 다름

`upgradeLegacyLorebook`은 본문을 보존하지만 상시 항목을 자동으로 `required`로 만들지 않는다. 키가 있으면 `keyed`, 없으면 `retrieve`가 되고 원래 정규식 문자열은 별칭/키 문자열로 복사된다. 선택 함수는 이 경로에서 `useRegex`를 평가하지 않는다. 기존 UI는 메타데이터를 만들 때 `legacy`로 두고 사용자가 체크해야 Grimoire가 활성화된다. **자동 전환 사고라고 주장하지 않는다.**

실제 카드로 동일 입력을 시험한 결과 두 판 모두 기존 방식20개(상시19개), 별도 메타데이터 조정 없는 Grimoire 전환0개였다. 별도의 정규식 전용 표본도 기존1개/Grimoire0개였다. 다른 입력에서 항상0개라는 뜻은 아니다. 원문이 삭제된 것도 아니다.

상시19개를 단순히 모두 `required`로 바꾸면 또 다른 문제가 생긴다. Grimoire 기본 상한8,000보다 상시 본문만10,247토큰이 커서 이 시험에서는 `BardLoreBudgetError`가 났다. 기본12개 제한은 **선택 문맥 항목**에 적용되며 필수 항목 개수 제한으로 해석하면 안 된다. 기존64,000 로어 예산은 Grimoire의 별도 상한을 대신하지 않는다.

태블릿 저장본에는 이미749개 Grimoire 메타데이터가 있고 모드는legacy다. 저장된 Grimoire 상한10,000도 이 o200k 상시 본문10,247보다 작다. 어댑터는 앞으로 만드는 자료뿐 아니라 기존 메타데이터와 `sourceHash`도 다뤄야 한다. 별칭의 쉼표 분리는 정규식 수량자 등에서 추가 의미 손실이 생길 수 있어 그대로 재사용할 수 없다.

Grimoire 도입은 ID/제목/원문 보존, 정규식과 한국어 별칭·보조키 대응, 상시 항목 명시, 적정 예산, 기존 메타데이터 이행을 검토해야 하는 후속 작업이다. 지금 즉시 켜는 것은 권하지 않는다. ### C. BardWiki 입력의 상태 봉투 경계 — 소스·합성 시험, 기기 사례 미관측

`projectConfirmedMemoryTurn`과 `projectRecentMemoryMessages`는 저장된 메시지 본문을 그대로 투영한다. 합성 `MGE_STATE` 봉투를 넣은 검사에서 봉투가 남았고, 뒤에서4,096자를 취하는 조회 문맥에서는 긴 봉투 때문에 앞의 서사 문장이 빠졌다. 서버 분석 조회도 같은 길이의 뒤쪽 문자열을 사용한다.

이는 약6,000자 합성 봉투로 확인한 **입력 처리 경계의 재현**이며 실제 모델이 잘못된 위키를 작성했다는 증거는 아니다. 실제 봉투 길이와 문제가 되는 조회 경로 실행을 확인해야 한다. 호출부는 위키 예산·현재 입력·문맥 변경 여부를 조건으로 최근 조회 문맥과 fallback 사본을 만든다(`index.svelte.ts:1700–1748`). 이름이fallback이라는 이유만으로 오류 발생 때만 실행된다고 추정하지 않는다. Life6.9의01/03 입력 필터는 그 모듈에만 적용되어 BardWiki까지 자동 보호하지 않는다. 이후 수정한다면 위키 분석/조회용 사본에서만 봉투를 제외하고 저장된 봉투·원본 대화·Lua 복구는 보존해야 한다. 광범위한 HTML 주석 삭제로 다른 자료까지 제거해서는 안 된다.

상위 조건은 서사 문맥 opt-in과 `prepareContext`의null아님이다(`index.svelte.ts:1669–1687`). 위 블록에 진입하면 최근 AI 응답4개를 기준으로 관련 사용자 입력을 선택한 사본에4,096자 경계를 적용해 임베딩 조회에 전달하고, 별도의fallback 사본도 생성한다(`index.svelte.ts:1711–1718`, AI응답0개일 때는 최근 메시지4개 폴백). 앞선 ‘최근4메시지’ 설명을 후속 사양 조사에서 정정했다. 서버가fallback을 실제 채택한 상황까지 재현한 것은 아니다. 저장본 통계의봉투0개는 해당 캐릭터 메타데이터에 `chat.message` 배열 자체가 없는 자료를 센 값이므로 **기기 대화에 봉투가 없다는 증거가 아니다**. 본문이 분리 저장된 실제 메시지 파일의 길이는 측정하지 않았다. 카드의 실제 구분자는 `<!--MGE_STATE\n`와 `\nMGE_STATE-->`이며, 합성 시험은 원본 봉투 파서 검사가 아닌 본문 투영의 길이 경계 시험이다.

근거: `src/ts/risubard/memoryAnalysisClient.ts:575`, `:621`, `:662`; `server/node/risubard-memory-analysis.ts:1171`; 기존 `releases/module_v6.9/README.md`.

### D. 기억 기능 중복은 조건부 위험

Life의 기억 생성/검색과 플러그인 주입, BardWiki의 자동 분석/조회는 별개이다. 저장본의 전역 `risuBardAutoWikiEnabled`는true지만 채팅별 재정의와 Life의 실제 실행 상태는 별도로 확인해야 한다. 둘 다 활성화하면 같은 사건을 다른 방식으로 정리하고 별도 요청/토큰을 쓸 가능성이 있다. 이번에는 전체 활성 경로와 실제 호출을 측정하지 않았으므로 이미 중복 비용이 발생한다고 단정하지 않는다.

권장 역할 구분은 **원문 로어=고정 세계관, 카드 Lua=게임 상태, 한 기억 체계=플레이 사건/관계**다. Life 전체에는 기억 외 기능도 있으므로 모듈/플러그인을 통째로 제거할 근거가 아니다. 또한 Lua의 `getLoreBooks`는 제목이 정확히 같은 기존 로어를 읽는다. 본문을 위키로 옮기거나 제목을 바꾸면 이를 쓰는 호출도 함께 검증해야 한다.

## 후속 순서 제안

1. 온라인 일반판의 현재 MGE 설정·채팅별 재정의와 이전 경로를 확인한다. 배포 카드 설정64,000/4/재귀꺼짐을 해당 캐릭터에 적용하는 안과 전역값 변경은 분리한다. 실제 요청 미리보기/로그에서 상시19개와 필요한 지역/인물 로어, 전체 문맥 한도를 확인한다. 저장/재시작뿐 아니라 입력 문맥 보존을 수용 기준으로 삼는다.
2. 기존 로어 모드를 유지한 상태에서 BardWiki에 들어가는 MGE 상태 봉투를 입력 사본에서만 제외하는 호환 수정을 검토한다. 저장/슬롯 복원과 Lua 상태는 그대로 둔다.
3. 대표적인 짧은 플레이와 과거 사건 회상으로 Life 기억/BardWiki의 역할을 비교하고, 장기 기억을 어느 쪽이 맡을지 결정한다. 기존 기억은 보존한다.
4. Grimoire는 별도 메타데이터 대응표와 한국어 키/예산 비교가 끝난 후 선택적으로 적용한다. 8,000토큰 기본값에 맞추기 위해 로어 원문을 임의 축약하지 않는다.

## 로컬 AI 작업 종료

사용자의 "로컬 AI 모델은 포기" 결정에 따라 GGUF/llama.cpp 추론판의 추가 개발·모델 선정·성능/발열 검증은 향후 작업에서 제외한다. 일반 RisuBard와 온라인 API 경로에 집중한다. **Android 앱 안에서 실행하는 Node 서버는 앱 구동 기반이며 AI 모델 추론과 다르므로 이 결정의 제거 대상이 아니다.**

기존 Offline 앱·모델 파일·새로 추가한 캐릭터/대화는 삭제하거나 옮기지 않았다. 향후 필요하면 일반판으로 자료를 이전하는 별도 작업으로 다룬다. 오프라인 글꼴/수식/파일 열기 등 이미 구현된 비추론 기능도 이번 검토로 제거하지 않았다.
