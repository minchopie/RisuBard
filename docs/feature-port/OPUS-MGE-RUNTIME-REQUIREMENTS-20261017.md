## 1차

# Opus 5.5 xhigh 교차 검수: MGE의 RisuBard 실행 조건 보고서

제공된 발췌만 검토했습니다. 새로 조회하거나 실기기에서 확인한 내용은 없습니다.

## 중대 오류

**1. "확인된 로어 선택 문제"는 과장입니다.**
- 근거는 합성 선택 함수 시험뿐입니다. 저장본에는 전역 `loreBookToken 800`, `depth 5`만 있습니다.
- 다음 두 가지는 증거에 없습니다.
  - 태블릿 MGE에 카드 설정(64000/4/false)이 실제로 적용되는지
  - 설치된 MGE의 해시
- "저장본 설정 800은 상시 1개 선택"은 800 + 재귀 true 조합의 결과입니다. 저장본에는 재귀값이 없습니다.
- 수정안: "전역 800이 적용되면 선택이 무너질 수 있음(합성 시험). 기기에 적용된 값은 미확인."

**2. 문맥을 늘려도 과거 대화가 더 전송되지 않는다는 주장은 근거가 없습니다.**
- 대상 문장: "12메시지 창 밖 과거 대화는 자동 전송되지 않음", "한도만 늘린다고 그만큼 쓰지 않음".
- `risuBardRecentMessageCount`가 메인 요청의 이력을 제한한다는 소스는 제공되지 않았습니다.
- 2048행은 출력 예약값에서 `currentTokens`를 시작하고 Wiki 메시지를 더한 뒤 조립을 이어갑니다. RisuAI 계열은 보통 남은 예산까지 이력을 채웁니다.
- 그렇다면 긴 채팅에서 200,000 상향은 입력 토큰, 지연, 비용을 실제로 늘릴 수 있습니다. 이는 '원활함' 목표와 충돌합니다.
- 수정안: 미검증으로 표기하고, 실험 항목에 "상향 전후 실제 입력 토큰 변화"를 추가합니다.

**3. 출력 예약의 의미를 잘못 서술했습니다.**
- 2950행의 입력 한도는 Wiki 메시지가 있으면 `maxContext−maxResponse`, 없으면 `maxContext`입니다.
- 두 경우 모두 removable 메시지를 비우는 방식으로 줄입니다. 따라서 "입력 제거 대 출력 축소" 이분법은 틀립니다.
- 비울 메시지가 없으면 `toomuchtoken` 오류로 생성이 중단됩니다(2954–2957). 보고서에 이 실패 경로가 없습니다.
- 2984–2987의 `outputTokens`는 주석상 "estimate"입니다. 이 값이 실제 송신 `max_tokens`를 줄인다는 사용처는 발췌에 없습니다.
- 조립 단계는 Wiki 유무와 관계없이 2048행에서 출력을 먼저 예약합니다.

**4. 온라인 전용 요구와 관련된 우회 경로가 빠졌습니다.**
- `modelPresetBinding.ts:70`: `localAI.available && enabled`이면 잠금, 채팅 설정, classic 경로를 모두 무시하고 로컬 프리셋을 반환합니다.
- 두 기기에는 Offline 후보33이 로컬 모델 설정과 함께 설치되어 있습니다(DEVICE-QA 25행).
- 수정안: 남은 검사 1번에 "일반 APK에서 localAI 비활성 확인, Offline APK로 MGE 시험 금지"를 명시합니다.

## 수정 필요

  - 모든 측정은 o200k 기준입니다.
  - Gemini 프로필의 권장 토크나이저는 gemma입니다.

## 2차

# 2차 검수: 남은 사실 오류

**판정:** 핵심 결론은 제공 소스와 맞습니다. 해당 결론은 130,000 우선 측정, legacy와 카드 로어 64,000/4/재귀 꺼짐, 12가 AI 응답 기준이라는 점, 문맥을 늘려도 응답 창이 풀리지 않는다는 점입니다. 아래는 아직 고쳐지지 않은 오류와 근거를 넘어선 서술만 적었습니다.

## 1. 프리셋 출력 폴백 (오류)
"출력값 미지정은 전역값으로 폴백"은 틀렸습니다.
- `resolvePresetMaxOutputTokens`는 사용자값 → schema 기본값 → `profileSnapshot.defaults` 순서로 찾습니다.
- 어디에도 값이 없을 때만 `db.maxResponse`를 씁니다(`modelPresetBinding.ts:148–155`, `index:1424–1425`).
- 따라서 사용자가 비워 둔 프리셋은 보통 30,000이 아니라 스키마나 프로필 기본값을 예약합니다.
- **수정안:** "프리셋 어디에도 출력값이 없을 때만 전역값".

## 2. useModelPreset 범위 (범위 오류)
- 바인딩은 **채팅별** 값인 `chat?.useModelPreset ?? false`를 읽습니다.
- 그보다 localAI 분기(`:70`)와 전역 lock(`:93–96`)이 먼저 적용됩니다.
- "태블릿 MGE는 useModelPreset=false"는 "MGE의 저장된 해당 채팅은…"으로 한정해야 합니다. 새 채팅은 `useModelPresetByDefault` 스냅샷에 따라 값이 달라질 수 있습니다.
- 제공된 안전 스냅샷에는 이 필드, 130,000/30,000, `reverse_proxy`가 없습니다. 출처를 `measurements.json`으로 명시해야 합니다.

## 3. outputTokens를 "기록용"으로 단정 (근거 초과)
- 발췌가 증명하는 것은 하나입니다. `requestChatData` 인자에 maxTokens가 없어서 `arg.maxTokens ?? db.maxResponse`(`request.ts:507`)로 간다는 점입니다.
- 추정값의 다른 사용처는 제시되지 않았습니다.
- **수정안:** "메인 요청 인자로 전달되지 않음(다른 용도 미확인)".
- `:507`의 `db`가 `requestSettings`인지도 제시되지 않았습니다.

## 4. 이전 로어 보고서 C의 "최근4메시지" (같은 유형의 오류 가능성)
- `memoryAnalysisClient.ts:588–618`도 `selectNarrativeWorkingMessages`를 쓰므로 **AI 응답 수** 기준입니다.
- 사용자 필터는 선택 뒤에 적용됩니다.
- 첫 메시지는 적격 응답 수가 한도 이하일 때 앞에 붙습니다.
- 임베딩용 사본이 이 경로에서 limit 4로 만들어진다면 실제 내용은 "4메시지"가 아닙니다. "응답 4개 + 관련 사용자 입력(+첫 메시지)"입니다.
- `:1700–1748`이 제공되지 않았으므로, 확인 후 정정하거나 조건부로 표기해야 합니다.
- 4,096자 꼬리 절단에 관한 결론은 유지할 수 있습니다.

## 5. "각12" 중 분석 창 (미입증)
- 스냅샷에는 `risuBardResponseMessageCount=12`만 있습니다. 분석 한도(`boundedLimit`)의 값과 출처는 없습니다.
- 응답 창 값도 `resolvedRisuBardSettings(currentChat)`를 통하므로 채팅별 재정의가 가능합니다. 전역값 12를 현재 유효값으로 단정하면 안 됩니다.
- 첫 메시지 포함 조건도 두 경로가 다릅니다.
  - 응답 창: 전체 AI 응답 수(OOC 포함) `< limit`
  - 분석: 적격 응답 수 `≤ limit`

## 6. 세부 문구
- **(a)** AI 응답이 0개면 `eligible.slice(-limit)`가 적용되어 실제로 전체 12메시지 제한이 됩니다. "전체 메시지12개 제한이 아님"에 이 예외를 한 줄 추가해야 합니다.
- **(b)** "관련 사용자12개"는 교대 대화일 때의 값입니다. 첫 선택 응답 앞에 사용자 입력이 연속으로 있으면 모두 포함됩니다. 지금은 예시 조건이 붙어 있어 허용 범위지만, 일반 규칙처럼 인용하지 마십시오.
- **(c)** `lorebook.svelte.ts:195–203`은 예산(전역 800)과 재귀(true) 폴백만 보여 줍니다. "전역800/5"의 깊이 5 폴백 근거는 이 범위에 없으니 인용을 분리해야 합니다.

- 버전의 `-debug` 접미사: gradle 발췌에는 `0.9.72-dev`만 있습니다.

## 최종 표적 검토

**판정: 확인된 사실 오류 없음.** 기기 성능과 하드웨어는 인증하지 않습니다.

**정밀도 보완 (오류 아님)**
- **1번:** 해석 순서는 스키마 필드별 `userValues[key] ?? field.default`입니다. 사용자 값이 null이 아니면서 무효(예: 0)이면 그 필드의 스키마 기본값은 건너뛰고, 다음 필드와 `defaults`로 넘어갑니다. 따라서 "어디에도 유효값이 없을 때만 폴백"은 이 경우를 포함하지 않습니다.
- **1·2번:** ModelPreset에 바인딩된 채팅의 입력 예산은 `preset.maxContext`(미설정 시 65000)를 컨텍스트 창으로 clamp한 값입니다. 전역 130000은 바인딩되지 않은 채팅에만 적용됩니다.
- **2번:** 측정값은 `mgeUsesPreset:[false]` 하나뿐입니다. "특정 채팅에 저장된 `useModelPreset`"이라는 필드 해석과 localAI의 실제 기기 상태는 측정값에 없습니다. 확인된 것은 코드상 우선순위(`localAI.available && enabled`)와 `nodeOnlyModelModeLock:"none"`입니다.
- **3번:** 두 재검사 분기의 "제거 후 실패" 동작은 제공된 소스에 없어 검증하지 못했습니다(반박은 아님). `requestChatData` 래퍼도 제공되지 않았습니다.
- **4번:** 4096 tail은 `buildBoundedNarrativeInquiryFallback` 본문이 없어 검증하지 못했습니다. 사용자 메시지를 제외하고 assistant 응답도 없으면 결과가 빈 배열일 수 있습니다.
- **5번:** `pinned ?? chat` 구조라서 pinned가 있으면 채팅 오버라이드 전체를 대체합니다. 키별로 병합되지 않습니다.
- **6번:** 25건 예시는 소스와 일치합니다. 깊이는 카드 `scanDepth`가 우선이고, 없을 때 `DBState.db.loreBookDepth`를 씁니다. 검색 경로의 깊이는 1입니다.
