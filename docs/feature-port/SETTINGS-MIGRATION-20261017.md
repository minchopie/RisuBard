# RisuAI USB → RisuBard 설정 초기화·선택 이전 — 2026-10-17

사용자가 범위를 **설정만 초기화**로 확정했다. TB710FU·SM-S938N 각각의 일반판과 Offline판, 총 4개 앱에서 초기화와 선택 이전을 완료했다. 제품 소스/APK 변경·설치·릴리즈 작업은 아니다.

- **GOAL:** 각 기기의 기존 RisuAI USB API 설정·모듈·플러그인·프리셋을 해당 기기의 RisuBard에 맞춘다.
- **MUST:** 설정만 초기화하고 앱의 기존 저장 API와 flush를 사용한다. 자체 검사 후 실제 Opus 5.5 Extra(xhigh) 검수로 근거를 확인한다.
- **KEEP:** 기존 캐릭터·채팅·페르소나·기억·저장 슬롯, 기존 라이브러리와 플러그인 데이터, Offline 모델·설정, 원본 USB 앱. 이후 사용자가 추가한 자료도 보존한다.
- **VERIFY:** 초기화 대상/이전 대상의 실제 저장값, 강제 종료·재시작 후 재조회, 참조 이미지 SHA-256, 보호 자료와 Offline 모델의 전후 비교.

각 앱의 계획에는 초기화 필드 198개, 이전 필드 167개가 있다. 기존 Default 프리셋은 보존하고 원본 기기별 프리셋 3개/2개를 추가했다. 이름이 충돌하는 Hypa/번역 프리셋은 `(RisuAI USB)` 접미사로 구분했다. 테마는 기본값으로 초기화했으며 활성 테마 프리셋의 미러도 앱의 정상 처리로 맞췄다. 모듈 ID는 원본 기기별로 유지했다. 원본의 전역 활성 모듈 목록이 비어 있어 임의로 전역 활성화하지 않았다.

API 자격정보는 비공개 로컬 경로에서 이전했다. `apiConfigured`는 키와 URL이 저장되어 있음을 뜻하며 실제 API 응답 성공을 뜻하지 않는다. Offline의 기기 내 AI가 켜져 있으면 기존 코드가 로컬 모델을 우선 선택하므로, 이전한 온라인 API 설정은 보관되고 로컬 생성 모드는 유지된다.

## 보존 및 검사 근거

1. 두 USB 앱의 전체 내보내기 스트림을 끝까지 해석하고, 네 대상 앱의 전후 TAR를 보존했다. 원본 USB 앱 데이터는 수정하지 않았다. 비밀번호·API 키·실제 DB·채팅·전체 백업은 Git 제외 경로에만 두었고 Claude에게 전달하지 않았다.
2. 적용 전 실제 해시와 `expectedHash`를 대조했다. 기존 API의 patch·flush·재조회로 적용했으며 DB 파일을 직접 덮어쓰지 않았다. 적용 후 앱의 정규화된 값과 비교했다. 첫 스마트폰 Offline 검사에서 JSON 속성 순서로 잘못 실패한 비교는 순서와 무관한 비교로 교정했고, 재적용하지 않고 저장값 일치와 후속 재시작으로 확인했다.
3. 15:45~15:46 KST에 네 앱을 각각 강제 종료·시작한 뒤 flush/read와 설정 비교를 통과했다. 이전 필드 불일치와 기본값 불일치는 모두 0개였다. 각 앱에서 모듈 이미지 134개의 실제 바이트를 다시 읽어 원본 SHA-256과 대조했다.
4. 태블릿 원본 백업에는 모듈 이미지 별칭 134개의 바이트가 빠져 있었다. 모듈 본문과 순서별 에셋 이름/유형이 같은 스마트폰 자료를 사용했고, 134개 모두 배포 원본 Life 6.9 `.risum`의 SHA-256과 일치했다. 태블릿의 기존 별칭 경로로 복구했다. 유실된 태블릿 원본 바이트 자체를 확인했다는 뜻은 아니다.
5. 스마트폰 모듈의 **선택적 아이콘 1개**는 두 원본 백업과 배포 모듈에도 없었다. 임의 대체하지 않았다. 본문 이미지 134개 복구/검증과 구분한다.
6. 전후 아카이브에서 채팅·기억·슬롯·페르소나·기존 이미지/프리셋 보호 파일을 비교했다. 일반판의 캐릭터 메타데이터 3건에는 차이가 있었지만 모두 설정 패치 직전 실제 DB에도 이미 있던 변경이었다. 나머지 보호 파일은 동일하며, 네 앱의 채팅·기억·슬롯 파일 바이트는 그대로였다. 모든 파일이 바이트 동일하다고 일반화하지 않는다.
7. Offline 모델 파일을 양 기기에서 별도로 해시했다: `9465e63a22add5354d9bb4b99e90117043c7124007664907259bd16d043bb031`. 모델 설정 파일은 전후 바이트 동일하고 문맥 4096/출력 512를 유지했다. 보관 개수·이미지 자동 정리·자동 위키·임베딩 설정도 전후 일치했다. 기존 플러그인 저장값과 폴더/정렬 기존 부분은 보존했다.

검사 범위는 계획에 열거한 필드와 보호 파일이다. 런타임 모델 레지스트리 캐시의 동일성은 보증하지 않는다. 플러그인은 네 앱에 `enabled=true`로 저장되었다. 스마트폰 Offline에서 시작 시 DOM 삽입은 관찰했으나, 모든 앱의 플러그인 권한/실제 모델 호출을 완주한 검사가 아니다.

## 공동 검수와 사용자 작업

실제 `claude-opus-5-5 --effort xhigh`에 비밀정보를 제외한 작업 코드와 검사 결과를 전달했다. 첫 호출은 출력 한도 오류로 완료하지 못해 승인으로 세지 않았다. 이후 초기화 검수, 적용 후 검수, 최종 검수의 유효 응답 3건을 받았다.

지적에 따라 비교 결과 배열의 단언, 기존 플러그인 저장값/정렬 보존 검사, Offline 설정/실제 모델 해시 확인, 자동 정리 설정 비교, 검증 범위 표현을 보완했다. 마지막 검수의 결론은 **설정의 적용·저장·각 재시작 시점의 유지 주장에 대해 확인된 차단 문제 없음**이다. 실제 원문은 [OPUS-SETTINGS-20261017.md](OPUS-SETTINGS-20261017.md)에 보존했다.

초기 네 앱 재시작 검사 뒤 스마트폰 Offline에 캐릭터가 추가되었고, 사용자가 직접 추가했다고 확인했다. 그 상태는 이전의 전체 캐릭터 배열 비교와 달라지는 것이 정상이다. 이를 오류로 간주해 되돌리거나 초기화를 반복하지 않았다. **캐릭터 추가 후의 실시간 DB 전체 재검사는 수행하지 않았다.** 과거 백업으로 통째로 복원하면 이후 사용자 작업이 사라질 수 있으므로 자동 복원하지 않는다.

## 후속 호환성 검토에서 확인한 제한 — 2026-10-17

앞선 저장·재시작 검사는 MGE 프롬프트 충분성을 검증하지 않았다. 태블릿 일반판 저장본의 캐릭터 loreSettings는 초기화 전부터 없었고 전역 loreBookToken은8,000에서800으로 초기화됐다. 실제 선택 함수의 합성 시험에서 상시19개 중13개→1개로 줄었다(재귀 기본true). 예산64,000만 적용해도 재귀true에서는14개, 카드 지정64,000/스캔4/재귀false에서는19개가 선택됐다. 이 결과는 단일 합성 입력/o200k/모듈 제외 조건이며 현재 기기 상태나 실제 요청 결과가 아니다.

설정 저장 검증의 통과를 카드 호환성 완료로 해석하지 않는다. 기존 작업에서 이 문맥 누락을 확인하지 못했다. 현재 상태 확인 후 해당 캐릭터에 카드 지정 설정을 적용하는 별도 후속이 필요하며 전체 백업 복원·재초기화는 하지 않았다. 상세: [구조·로어 호환성 검토](LORE-COMPATIBILITY-20261017.md).
