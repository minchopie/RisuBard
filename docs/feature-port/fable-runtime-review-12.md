## 1. Verification

### 1.1 Callers and source selection — verified

`loadPersistedFullDatabase` is called from exactly the four sites the response names: `ensureChatStore` (`runMaintenance: true`), the `/api/patch` cold load (default options → `runMaintenance: false`, same as the old `decodeDatabaseWithPersistentChatIds(fileContent)`), `persistChatStoreWithoutCache` (default options), and the shutdown base fallback. Gate: `canonicalProjectionReady && !externalEditSession.isActive()` after `await migrateRemoteBlocksIfNeeded()`; since every branch of that function marks the migration done and a run that rewrites `database.bin` calls `invalidateDbCache()` (which clears `canonicalProjectionReady`), this is equivalent to `prepareDatabaseRead`'s `isRemoteMigrationDone()` gate. The legacy lane is byte-for-byte the old `ensureChatStore` legacy branch (`kvGet` → `decodeDatabaseWithPersistentChatIds(raw, options)`); `raw` is read after the outer migration, so the inner idempotent call never sees stale bytes. KEEP (legacy migration) holds.

Behavioural change in `persistChatStoreWithoutCache`: it was blob-first with a plain `decodeRisuSave` (no maintenance); it is now canonical-first with maintenance normalisation. Reachable only when `fullChatStore` is set and `dbCache` is empty (backup import, snapshot restore, stub-flag-loss abort, patch-apply failure) — in all of those the maintenance pass has already run or there is nothing to fix, so no extra writes in practice. The canonical-first choice is also safer for the chat-direct lane (`syncLegacyChatState` validates topology against the sidebar, which the canonical export matches by construction).

`prepareDatabaseRead` keeps its own metadata-only selector; `readCanonicalChatBeforeHydration` keeps a third gate that additionally refuses on `hasExternalChanges()`. Three gates remain (design smell, see §3.4).

### 1.2 Failure propagation — verified

Only `userDataRepository.exportLegacyDatabase()` is inside the `try`; `prepareDatabaseWithPersistentChatIds` (and any maintenance `kvSet`/`persistCanonicalProjection` it performs) is outside, so maintenance failures still propagate — the response's "only export failure falls back" claim is accurate. Blob-lane errors propagate. A `null` result yields: `ensureChatStore` → empty `Map` (pre-existing); `/api/patch` → `dbCache = {}` (pre-existing); `persistChatStoreWithoutCache` → explicit throw inside the `try`, so it is recorded with `errorStage: 'decode'`, marks the direct-write tracker unsafe and the cache unverified, then rethrows (strictly safer than the old `exportLegacyDatabase()`-on-empty-root, which would have written an empty sidebar); shutdown → `stripChatsFromDb(null)` returns `null` → explicit throw → outer catch, exit 1, no recovery file. Previously `stripChatsFromDb(exportLegacyDatabase())` threw on any stale sidecar; now the recovery file is suppressed only when neither source is readable. Empty data is never fabricated into a save — claim verified.

### 1.3 External-edit byte preservation — verified for the blob-present configuration

`uncached-chat-flush` `externalBeforeRead` edits `metadata.json` after boot (stale sidecar), then asserts the file bytes after `GET /api/chat-content/one/0` (returns the pre-edit chat), after `GET /api/db/stats/characters`, and after the chat POST (409). Source trace: `readCanonicalChatBeforeHydration` refuses (`hasExternalChanges()`), `ensureChatStore` → export throws checksum mismatch → blob lane → no `needsPersist` → no writes. If a legacy root did need maintenance here, `persistCanonicalProjection` fails at `external-change-check` (CFC) before any file operation, so the hand edit still cannot be overwritten (the blob `kvSet` would happen first — pre-existing). The hydrated `dbCache` is the pre-edit state, which is the correct baseline for `/api/external-changes` `inspect`. Repro log shows the pre-fix 500 ("Canonical file checksum mismatch: characters\one\metadata.json"); fixed log passes. Note the exact scenario is "edited while open before first read": an edit made while closed with a stale sidecar is re-committed with a fresh checksum by the constructor's `reconcileCanonicalProjection({externalEditing:true})` at boot (and left pending for review), so the fallback would not be needed for that case unless the JSON is invalid.

### 1.4 Concurrency guard — verified

`ensureChatStore` re-checks `fullChatStore` after its only `await` and before `initChatStore`; `dbCache` is seeded only when empty. `concurrentStats` (delayed first `decodeRisuSave` on a blob-only root) passes in both repro and fixed logs. A queued `/api/patch` cold load concurrent with an unqueued hydration decodes the same committed state and its `if (!fullChatStore)` guard prevents a second `initChatStore`. The pre-existing caveat stands: unqueued GET hydration can perform maintenance writes outside the writer queue (synchronous, cannot interleave with a transaction).

## 2. Confirmed items (source-proved)

1. **Blanket catch, path not logged.** The `catch` falls back on any error from `exportLegacyDatabase()`, not only `CANONICAL_FILES_CHANGED`, and logs `error.code || error.name` without `error.message` (the file path). Consequence is hypothetical (§3.2); diagnosability loss is real. Same pattern as `prepareDatabaseRead`.
2. **Redundant work, harmless.** Blob lane calls `migrateRemoteBlocksIfNeeded` twice (marker short-circuits); shutdown calls `ensureChatStore()` then `loadPersistedFullDatabase()` again when `fullChatStore` is set but `dbCache` is empty (import/snapshot lane only).
3. **Test pins an acknowledged-gate behaviour.** After a disk-full-retained journal, boot `recoverTransactions` completes the app's own write; the accepted revision still predates it, so `/api/patch` returns 409 `EXTERNAL_CHANGES_PENDING` and `/api/external-changes` lists the app's own files as external. The new assertion is correct for current source and does not bypass the guard, but it codifies R10 §3.1/§3.3. The read-first order adopts it; the patch-first order hands it to the review UI.
4. **Harness.** `full-write-failure` constructs a second `createUserDataRepository` on the live root before `/api/patch`; that constructor runs journal recovery and may commit a sidebar — not read-only against a running server (passes today because nothing is pending/changed). `pending-flush-retry` now slices `loadPersistedFullDatabase` with `with(deps)`; `logger` and `decodeDatabaseWithPersistentChatIds` are absent from `deps` and merely unreached (R11 §2.3 fragility persists).

## 3. Unverified risks (hypotheses)

1. **Deferred-compatibility roots.** When the blob was removed by a canonical-only flush, the fallback `kvGet` triggers `rebuild('read')`, which calls the same `exportLegacyDatabase()` and throws again. So on an Android/`deferCompatibility` root a stale sidecar plus a pending patch with `fullChatStore` still null at shutdown still suppresses the recovery file (metadata-only loss; chat bodies remain on disk). Not a regression (R9 and R10 both failed here); untested.
2. **Blanket catch × blob-ahead.** If a prior canonical failure left the blob ahead and a later canonical read fails for a reason that does not change the fingerprint (transient I/O), hydration would take the attempted blob and the next flush could resurrect the failed write — the R9 §4.1 hybrid, now narrowed to this corner. Narrowing the catch to the checksum code (requires `readVerifiedJson`'s error code, not supplied) would close it.
3. **Blob never re-synced after a canonical-failed restart.** `/api/read`'s canonical lane does not touch the blob, so `/api/db/stats/characters`, `/api/backup/export`, settings-estimate and orphan cleanup read the attempted blob until a write-triggered flush. Pre-existing blob-ahead window; out of this delta.
4. **Hydration during a pending review.** A tool that rewrites both file and sidecar passes the export; `fullChatStore` then holds post-edit chat bodies while `dbCache` keeps the app baseline, and "keep app version" persists those bodies (bytes are still backed up by `backup(review)`). Originates in R10's canonical-first hydration; the delta adds the stale-sidecar/blob divergence. Depends on unsupplied review semantics for chat files.
5. **Boot-time recovery throw** (`createUserDataRepository` constructor) remains untested; `db.cjs` shows no degraded-mode handling.
6. **Unverifiable here:** before-file hash `00250fad…`; `maxWorkers 4`; client request order for resumed tabs; `file-store.cjs`, writer and revision-store internals.
