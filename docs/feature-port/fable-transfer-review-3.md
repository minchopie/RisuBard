## 2. Proved defects (deterministic trace, no supplied test executes them)

**D1 — Painter structural inlay references defeat chat deduplication on every repeat receipt (medium, shared core).**
`applyPlaySet` assigns every inlay item a fresh `crypto.randomUUID()` when there is no prior generation (`ids.set(item.id, … kind !== 'inlay' && … ? oldId : crypto.randomUUID())`), and `remapRecord` writes that UUID into `/bardPainter/results/N/assetId` and `…/referenceAssetId`. `applyCharacterChats` then hashes that staged chat with `chatFingerprint`, whose `normalize` only rewrites `assets/…` strings and `{{inlay::…}}` tokens; a bare UUID is left in the hashed value. Consequences: (a) B receiving the same archive twice: stored `risuTransferSource.hash` contains receipt-1's UUID, receipt-2 computes a different UUID → `old` not found via hash; the legacy loop re-hashes the stored candidate (receipt-1 UUID) → still ≠ → chat appended again, `mode: 'new'`. (b) Origin return: A's candidate carries `assetId: 'painter-result'`, incoming carries a random UUID → duplicate on A. Every chat that used BardPainter loses the idempotent-receipt guarantee that the non-Painter tests prove. The Painter test receives once only. Fix: in `chatFingerprint`, locate the chat item (`generation.ids[item.id] === chat.id` holds for both staged and candidate chats) and replace the value at each reference pointer whose target is an inlay item with `'inlay-sha256:' + target.hash` (or reverse-map any string equal to a local inlay ID through `generation.ids`). Test: receive a Painter archive twice and return it to origin; assert chat count unchanged and `duplicate`.

**D2 — Export-side sanitisation is not mirrored in the candidate fingerprint; origin return duplicates any chat with `promptInfo.promptText` or chat-level gallery entries (medium, shared core).**
`sanitizeTransferChat` → `sanitizeTransferMessages` deletes `message[].promptInfo.promptText` on the export copy; `selectTransferGallery` drops gallery slots. The incoming staged chat is therefore sanitised, but when A receives its own chat back, `chatFingerprint(candidate = A's raw local chat, legacy)` hashes the unsanitised record (its delete list covers `id/modules/bindedPersona/playContext/risuPlayContext/risuTransferMedia/risuTransferSource/folderId/isStreaming/activeStreaming…` only). Hashes differ → `old` undefined → a second copy is appended on the origin. B-side re-receipt is unaffected (B stored the sanitised copy), so only the "returning an unchanged export to its origin" / "roundtrip" guarantee breaks, and only when those fields exist locally — the project's own fixtures (`slotChat`) treat `promptText` as realistic. Fix: apply the same projection (promptText removal, gallery filter) inside `chatFingerprint` or fingerprint a `sanitizeTransferChat`-equivalent clone of the candidate. Test: origin message with `promptInfo.promptText`, export → receive on B → return → assert single chat.

**D3 — Chat-level and slot gallery filters use only the chat's own ID, not the selected set (low–medium; explicit, not silent; contradicts R2 wording).**
`snapshotPlaySet`: `selectTransferGallery(ch, new Set([selectedId]), selectedId, excluded, selectedId)`; `capturePlaySetMemory`: `new Set([manifest.sourceChatId])` although `chatIds` is in scope. The inventory describes `risuBardGallery` on a Chat as a *previous-chat* gallery, so its entries typically carry other chats' `sourceChatId`. Exporting chats A and B together still drops A's excerpts sourced from B. The character-level call correctly uses the full selected set. The gallery test only covers the character level plus a legacy (owner-less) chat-level slot. Fix: pass the selected set at both call sites. Also log category pruning and `activeStreamingDisplayOptimizationMode` removal to `excluded` for consistency.

**D4 — 2-C residual (low).** See 2-C above: workspace-file `Unsafe Bard workspace path`, `safeStatus` errors, and three slot-enumeration errors carry no location; `workspacePath` is the realistic one.

**D5 — `items` array aliasing between the v1 `snapshot.manifest` and the attached v2 manifest (low, latent).**
`attachPlaySetMemory` does `{ ...snapshot.manifest, version: 2, bard }`, so `items` is the same array; `finalizeSnapshotLineage` then mutates `item.parent` in place. When the v1 pass took the known-reuse branch, the v1 object (still claiming the known revision/parent/ancestors) now has item parents recomputed against the latest generation — the inverse of the original 2-A inconsistency, on the v1 object. Harmless today because nothing uses `snapshot.manifest` after attach; it becomes a defect the moment the pending "v1 compatibility export without Bard" writes that object after attaching. Fix: copy items in attach (`items: snapshot.manifest.items.map(i => ({ ...i }))`) or have finalize build a new array.

## 3. Unverified risks (hypotheses; design inputs)

- **H1 — chat-only receiver accepts v2 and records it (carried from 3-7, now codified).** `applyCharacterChats` validates v2 via `validateBard`, discards every Bard block, stores the v2 manifest with `characterChats: true`, and later marks the same archive `duplicate`. The test "Bard memory and slot revisions participate in chat deduplication…" locks this behaviour in. Decide before wiring: reject v2 at this entry point or flag the generation "Bard not applied" and let the future journaled receiver complete it. The same accept-and-discard holds for `applyPlaySet` if a full-play v2 archive ever reaches it.
- **H2 — 2-D behaviour change for whole-field paths containing whitespace at keys other than `image/icon/uri`** (e.g. `additionalAssets`/`emotionImages` entries): previously passed whole to `asset()` (which allows spaces), now fall to the extractor and are truncated at the first non-`[A-Za-z0-9_.-]` character → spurious `Missing local asset: assets/foo`. RisuAI hash-names saved assets, so realism is low; unverified.
- **H3 — gallery/Painter IDs are not remapped on receipt**, so a receiver's re-export drops every character-level gallery excerpt (`sourceChatId` is the sender's) explicitly into `excluded`, and `bardPainter.anchor.chatId/characterId` keep sender values (`rebindPainterChatScope` is not called by `applyCharacterChats`). R2 lists this as pending; stating the concrete second-hop loss so it is designed for.
- **H4 — pending-compression inlay replacement** (previous 3-1), **frozen-content references to deleted assets/inlays** (3-2), **`_placeholder` slots** (3-3), **service-wrapper junction path** (3-4), **transfer-scope fields inside slot `chat.bin`** (3-6: `risuPlayContext`, `risuTransferSource`, `modules`, `bindedPersona` are not removed by the frozen path and are not subject to `validateRecords`), **Bard-only changes creating new chat versions** (3-8, now by design per the dedup test), **non-deterministic slot enumeration order in `manifest.json`** (3-9) — all unchanged, none addressed by R2 and none claimed.
- **H5 — `exportStateHash`/`appliedHash` ignore Bard files**, so the origin's "unchanged since export" guard does not see local Bard edits; relevant only once a Bard receiver uses `decideImport`'s `update` mode.
- **H6 — `playSetMemoryMaterials.text()`** throws a pathless UTF-8 decode error for an invalid `.json/.md/.txt` material; slot chat re-encoding assumes the MessagePack codec is round-trip stable for every chat field (codec not supplied).

## 5. Verdict (export/archive scope only; physical installation HOLD stands; no release approval)

R2's five claimed fixes are real: 2-A, 2-B (as narrowly stated), 2-D and 2-E are confirmed by code and by the supplied tests, 2-C is partially done. No original data is mutated anywhere in the traced paths, and every omission except category pruning and one transient UI flag is recorded in `excluded`. The new Painter structural references and the live-chat sanitisation, however, were added without updating the shared `chatFingerprint`, producing two concrete regressions in the common core the receiver will depend on: D1 (Painter chats duplicate on every repeat receipt) and D2 (origin return duplicates chats with recorded prompts or chat-level galleries). Both are small, symmetric fixes with obvious tests. D3 is a one-line policy correction at two call sites; D4/D5 are minor. Nothing here changes the archive format beyond what 2-B already changed, so these can be closed before the format is first used. The export/archive core remains at "internal review passed with follow-ups", not release-ready, and the receiver remains unimplemented.
