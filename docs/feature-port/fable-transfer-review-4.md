# Independent follow-up review — Fable 5.1 export/archive and character-chat planner (R3)

**Evidence basis.** Read-only trace of the supplied `protocol.ts`, `snapshot.ts`, `apply.ts`, `characterChats.ts`, `importer.ts`, `play-set-archive.cjs`, `play-set-memory.cjs`, `risubard-memory-save-store.ts`, `memorySaveCodec.ts`, `bardPainter/types.ts`, `chatScope.ts`, the inventory doc, five test files and three logs. "Proved" means a deterministic trace through this code; nothing was executed. Limits: (a) 47 of the 103 "shared" tests (the block from "explicit missing-icon export…" to "an explicitly id-less running chat…") come from a file that is not supplied, so only their names are confirmed; the remaining 56 names match the supplied files (33 + 15 + 8) and the memory count (8 + 17 = 25) matches too. (b) `tmp/transfer3-final-types.log` is empty; that is consistent with a clean `tsc` run but identifies no tree, and R3 itself says the strict pass predates the final `scan` edit (`/^\/(?:additionalAssets|emotionImages)\/\d+\/1$/`). The strict-TS claim is therefore unverified for the reviewed source. (c) The "server 1158 pass / EPERM rename" claim has no supplied log. (d) The repro log shows the three feature tests failing before the fix at exactly the lines R2's D1 (repeat receipt → `'new'`), D2 (origin return → `'new'`) and the gallery remap (`'ch'` ≠ UUID) predicted, so those tests do exercise the defects.

## 1. R3 claims checked against code

**D1 (Painter inlay refs in fingerprint) — confirmed.** `chatFingerprint.normalize` now carries a JSON pointer; for `isPainterInlayPointer` it maps the string through `generation.ids` to the inlay item and hashes `'inlay-sha256:' + item.hash`. Trace of the painter case: receipt 1 stages a random inlay UUID → normalized; receipt 2 stages a different UUID → same normalized value → first lookup by `risuTransferSource.hash` succeeds → `duplicate`. Origin return: candidate `assetId: 'picture'` resolves through A's export generation (`localIds` inlay → `'picture'`) to the same inlay item hash, provided the inlay record hashes identically on both sides. That equality depends on `originalId`, which R3 stabilised: `applyPlaySet` now records `inlayOrigins[localUuid] = originalId`, `applyCharacterChats` copies it into `risuTransferMedia.inlayOrigins`, and `snapshot.inlay()` reads `activeScope.inlayOrigins[actualId]` — so B's and C's re-exports write `originalId: 'picture'`, not their local UUIDs. The A→B→A, A→B→C→A and repeat paths in the feature test are consistent with this trace and the log says pass.

**D2 (candidate projection) — confirmed.** `chatFingerprint` now calls `sanitizeTransferMessages` and `selectTransferGallery` on the copied candidate before hashing, mirroring `sanitizeTransferChat`'s `promptText` deletion and the gallery filter/category pruning. The delete list already covered `isStreaming`/`activeStreaming…`. Residual mismatches that are *not* mirrored: cold-storage hydration and `_placeholder`/`_stub` (see D-R3-2).

**D3 (full selected set) — confirmed at both call sites.** `snapshotPlaySet` passes `new Set(selectedChats ?? [])` for the chat-level gallery; `capturePlaySetMemory` passes `new Set(chatIds)` for slots. Gallery pointers are declared references (`isGalleryChatPointer`, expected kind `chat`), `validateManifest` keeps ownership on `/chats/N` only, `remapRecord` rewrites only the declared pointer, and `applyCharacterChats` re-maps imported records' `sourceChatId` after final IDs are chosen. Category pruning and `activeStreamingDisplayOptimizationMode` removal are now logged to `excluded`. Behavioural consequence in D-R3-3.

**D4 (path diagnostics) — confirmed with small residuals.** `capture()` wraps `workspacePath` with `relative(root, path)`; every `safeStatus`/`metadata`/`walk` error carries the relative path; slot enumeration errors carry `item.name`/`slotId`; `text()` carries the label (test asserts `broken.md`). Still pathless: `workspacePath(saved.path)` inside the slot loop (wrapped only with the slot label, not the offending page path) and the un-wrapped `decodeMemorySaveChat` in `playSetMemoryMaterials` (should not fail, since capture already decoded the same bytes). Note the wrapping for unsafe workspace file names is trace-only: the test host is Windows, where such names cannot be created.

**D5 (items aliasing) — confirmed.** `attachPlaySetMemory` builds `items: snapshot.manifest.items.map(item => ({ ...item }))`; `finalizeSnapshotLineage`'s in-place `item.parent` writes and `Object.assign(manifest, clone(known))` touch only the new object. The regression test asserts the v1 manifest is unchanged through the reused-ancestor path.

**H2 (structural whitespace paths) — confirmed as stated.** Index-1 entries of `additionalAssets`/`emotionImages` are now whole-field. Module `assets[N][1]` and any other key still go to the no-whitespace whole-field regex and then the extractor, so a module asset path containing a space is still truncated; realism remains low.

**H1 — status unchanged, but the consequence is now locked in.** `applyCharacterChats` validates v2 via `validateBard`, applies no Bard block, stores the v2 manifest with `characterChats: true`, includes `orderedBardWorkspace` in the chat fingerprint, and returns `duplicate` on any later receipt of the same revision. The test "Bard memory and slot revisions participate in chat deduplication…" asserts this. R3's statement that the planner is not a public endpoint is accepted; the gate in §4 follows from the fact that once any host calls this planner for a v2 archive, the Bard portion of that revision can never be applied by a later journaled receiver without new logic.

**Original data / declared fields / no text rewriting.** All new remaps are pointer-declared; the regex replacement in `normalize` is a hashing projection, never persisted. New export-copy modification not previously listed: `selectTransferGallery` backfills `slot.sourceChatId = owner` for legacy owner-less slots (structural, declared, not logged — inventory doc does not mention it). Clone/copy discipline holds (`clone(input)`, `copy(chat)`, `copy(database)`, temp copies for slot bytes); the feature test's `JSON.stringify(db) === before` and the slot-bytes assertions cover it.

## 2. Proved defects (deterministic trace; no supplied test executes them)

**D-R3-1 — Legacy candidate lookup consults only the first generation that maps the candidate; with D3's generation-dependent gallery projection this duplicates an unchanged chat on origin return (low–medium, pre-existing root cause, amplified by R3).**
`applyCharacterChats`: `const legacy = list(registry.generations).map(row).find(g => row(g.ids)[item.id] === candidate.id)` — `find`, not every match. Repro on A with chats X (gallery slot `sourceChatId: 'Y'`) and Y: export [X] → G1 (slot excluded at export); export [X, Y] → G2 (slot kept, declared). `recordExport` stores both (`existing` reuses the instance, revision differs). B receives export 2, re-exports [X_B, Y_B]; staged X normalizes to `'chat-origin:Yp'`. On A: X has no `risuTransferSource`; `find` returns G1; `chatFingerprint(X, G1)` builds the set `{X}` so the slot is dropped → hash ≠ staged → X appended a second time (Y dedups via G2). The same `find`-first picks G1's asset hashes for `assets/...` normalization, so an image re-exported with new bytes in G2 and returned unchanged also duplicates. Fix: try every generation mapping the candidate (latest first) or project both sides against the incoming archive's chat set translated through any generation's ids. Test: two exports with widening selection, return of the second, assert one X.

**D-R3-2 — Cold-stored chats on the origin can never be matched on return (low–medium, pre-existing, same class as D2).**
`snapshotPlaySet` hydrates `message[0].data` starting with `\uEF01COLDSTORAGE\uEF01` through `source.cold` (and may replace `scriptstate`/`hypaV3Data`/`localLore` when the cold payload is an object). `chatFingerprint` has no source access and hashes the raw candidate, whose first message is still the header. Hash ≠ staged → a hydrated copy is appended next to the cold original. The snapshot test fixture "real schema snapshot hydrates cold chat" uses exactly this representation. `_placeholder`/`_stub` candidates fail the same way (neither key is in the delete list). Fix options: host hydrates cold/placeholder chats before calling the planner (gate), or give `chatFingerprint` a cold reader; either way add a return test with a cold origin chat.

**D-R3-3 — Chat identity now depends on companion selection through gallery references (proved behaviour; defect only if selection-independence is the intended guarantee).**
Because chat-level and slot galleries keep every excerpt whose owner is in the selected set, the same unchanged chat exported with different companions produces different records, revisions and fingerprints. Repro on receiver B: receive X alone (slot → Y excluded) → later receive X+Y together (slot kept) → first lookup fails (stored hash lacks the slot), legacy loop fails for the same reason → second X on B. The inventory describes `risuBardGallery` as a *previous-chat* gallery, so excerpts referencing earlier chats are the normal case, making this common once users export predecessors. The test "unchanged chats deduplicate across different set IDs, names and selection context" has no gallery, so it does not detect this. Options: accept and document (receiver gets the fuller copy), or exclude gallery slots from identity (hash the chat without `risuBardGallery`) and merge galleries on receipt. Decide before the format is used.

**D-R3-4 — D4 residuals (low).** `Unsafe Bard workspace path` raised by `workspacePath(saved.path)` for a saved-page list entry is wrapped as `Memory save <id>: …` without the page path; `decodeMemorySaveChat` in `playSetMemoryMaterials` is unwrapped.

**D-R3-5 — H2 residual (low).** Module `assets[N][1]` paths with whitespace still truncate to `assets/<prefix>` and report a spurious missing asset.

## 3. Unverified risks (hypotheses; design inputs)

- **H-R3-1 — Painter-chat identity is bound to inlay record metadata across devices.** The D1 normalization hashes the inlay *item* (`metadata`, `originalId`, `data`, `mime`). If the receiver's inlay store rewrites `name/width/height/ext` or the staged Blob `type` differs from the sender's, B's re-export produces a different inlay hash and origin return duplicates the chat. The test uses the same `inlay()` stub on both sides. The `{{inlay::}}` token normalization has had the same dependency since before R2; D1 inherits it for Painter pointers. Needs a test with divergent inlay metadata or a decision to normalize on blob hash (`/data` target) instead of record hash.
- **H-R3-2 — Pre-R3 received chats lack `risuTransferMedia.inlayOrigins`.** For them, `snapshot.inlay()` falls back to the local UUID as `originalId`, the inlay hash changes, and origin return of a Painter or `{{inlay}}` chat duplicates. Only matters if development databases received chats before this change.
- **H-R3-3 — `find`-first also affects fingerprint asset hashes** (see D-R3-1) and the receiver's cold storage: if the app later cold-stores a received chat and drops `risuTransferSource` from the live stub, repeat receipts fall into the legacy loop with a header-only candidate.
- **H-R3-4 — Painter fields scanned only by the regex extractor:** `imagePreset.values`, `conversation[].text`, `draft.*` text. Any bare inlay UUID there is neither collected nor relinked; `assets/…` text is collected as a literal alias. Unknown whether real data puts asset IDs there.
- **H-R3-5 — Carried unchanged:** H3 (`bardPainter.anchor.*` and gallery `sourceChatId` inside slot `chat.bin` keep sender values; `rebindPainterChatScope` not called), H4 (pending compression, deleted frozen references, placeholder slots, transfer-scope fields inside `chat.bin`, non-deterministic slot order in `manifest.json` bytes), H5 (`exportStateHash`/`appliedHash` ignore Bard files), H6 (msgpack round-trip stability is evidenced only by deep-equality tests, not byte identity).
- **H-R3-6 — Verification gaps:** strict TS for the current tree (empty log, run predates last edit); the 47 unsupplied tests; the server-suite claim.

## 4. Required integration gates (not counted as implemented; must be settled before any host wiring)

1. **v2 at the chat planners.** Either reject `manifest.version === 2` in `applyCharacterChats`/`applyPlaySet` until the journaled Bard receiver exists, or stamp stored generations with an explicit `bardApplied: false` that the receiver and the `duplicate` decision consult. Without one of these, the first v2 receipt permanently blocks Bard application for that revision (H1, now locked by the dedup test).
2. **Hydration before apply.** The host must hydrate cold characters/chats and `_placeholder`/`_stub` chats on the receiving side before calling the planner (D-R3-2); otherwise chats are appended into cold placeholders or duplicated.
3. **Staged asset/inlay cleanup.** `applyPlaySet` assigns fresh inlay/asset copies on every receipt; when `applyCharacterChats` returns `duplicate` or dedups some chats, the host must discard the unused staged media. The planner gives no list of unused ids.
4. **Existing-card gallery merge.** When the target card already exists, incoming character-level gallery excerpts are dropped silently — not in `excluded`, not in `ApplyResult`. Surface them (e.g. an `unapplied` list) or merge; R3 defers the merge.
5. **Legacy generation lookup** (D-R3-1) and the **gallery identity policy** (D-R3-3) should be decided before fingerprint-based dedup is relied on by the receiver.
6. **Unchanged from before:** journaled v2 receiver with `ImportQueue` barrier; ID relinking for `chat.bin`, `risubard-save.json`, page hashes/turn receipts, wiki `source_messages`, Painter anchors, slot-embedded gallery `sourceChatId`; v1 compatibility export without Bard plus notice; API binding retention (`bindedBotPreset`/`useModelPreset`/`modelBinding`) per the inventory's `nodeOnlyModelModeLock` note; UI/transports/temp cleanup/`cleanup()` wiring/no-generation-during-export; Windows run.
7. **Documentation.** Inventory doc still lacks: live-chat `promptText` exclusion, local-ID exclusion from revision, 2-D/2-E rules, the gallery owner backfill, and the fingerprint normalization rules (Painter/gallery/prompt projection).

## 5. Verdict (export/archive and planner scope only; physical installation HOLD stands; no release approval)

R3's five fixes are real and are proved by both code trace and the supplied tests: D1 and D2 are closed for the paths the feature test exercises (repeat receipt, A→B→A, A→B→C→A, exact origin preservation), D3 is applied at every call site with declared edges and post-dedup remapping, D4 and D5 are done with minor residuals, H2 is handled for the two structural paths. No original chat, slot or DB is mutated in any traced path, and every omission except the gallery owner backfill is now recorded in `excluded`. What R3 did not address is the lookup logic around those fingerprints: the legacy candidate search still trusts the first matching generation (D-R3-1), the candidate projection still cannot see cold-stored content (D-R3-2), and D3 has made chat identity selection-dependent in the common "gallery of previous chats" case (D-R3-3). None of these corrupts data — the failure mode is always an extra copy with the original untouched — but all three defeat the dedup guarantee the receiver is being built on, and none is covered by a supplied test. The strict-TS state of the reviewed tree is unverified. The export/archive core stays at "internal review passed with follow-ups"; the receiver remains unimplemented and the gates in §4 are prerequisites, not options.
