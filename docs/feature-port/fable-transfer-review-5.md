## 1. R4 fixes checked against code

**D-R3-1 (legacy lookup consulted only the first mapping generation) — fixed, by trace and test.** `applyCharacterChats` now builds `generations = registry.generations.filter(g => g.ids[item.id] === candidate.id).reverse()` and tries `chatFingerprint(candidate, legacy, …)` for each, newest first, breaking on the first match. The `filter(...).reverse()` is on a fresh array; the registry is not mutated. Trace of the new test: A exports [X] (G1, slot excluded), then [X,Y] (G2, slot kept, `exportGeneration` reuses G1's instance), B receives wide and returns [X_B,Y_B]; on A the staged X normalizes its slot to `'chat-origin:'+Yportable`, candidate `ch` has no `risuTransferSource`, generations are [G2,G1], G2's projection keeps the slot and G2's `ids[Yportable]==='ch2'` yields the same token → match → `duplicate`, two chats. Two side benefits follow from the same loop: the `find`-first asset-hash normalization R4 noted is gone, and v2 export generations that `recordExport` stores on an origin (whose fingerprints include `orderedBardWorkspace`) can no longer shadow an older v1 generation when a v1 copy returns.

**D-R3-2 (cold/stub/placeholder candidates) — fixed for every case the planner can see; non-mutating.** Two checks: `existing?.coldstorage` throws before any chat work, and inside the legacy loop a candidate that is mapped by at least one generation (`generations.length`) and is `_stub`, `_placeholder`, or whose `message[0].data` carries the cold header throws `Hydrate the matching chat…`. Both throws occur while only the local `db` copy and the staged `generation` have been touched, so the caller's `database` is untouched — the four-case test's `JSON.stringify(original)===before` matches the trace. Keying on `generations` mapped to *this* `item.id` means unrelated cold chats on the target card never block a receipt. One scoping note: an unmapped cold candidate is still skipped silently, but an unmapped candidate can never deduplicate anyway (the loop is generation-driven), so this reduces to the pre-existing precondition that the host persists `recordExport` after every archive write. All four cases would fail pre-fix (the 'cold' and 'stub' cases would append; the 'character' case would deduplicate because the test keeps the chat body intact), so the tests are sensitive.

**D-R3-3 (selection-dependent identity) — accepted as policy; code and tests are consistent with the stated policy.** Receiving X alone and then X+Y leaves old X, a fuller X and Y (`richer` asserts three chats, `first` still one). The origin-side mirror of this policy is not covered and is reported in §2.

**H1 (v2 at the chat planners) — fixed; no false acknowledgement path remains inside the planners.** `applyPlaySet` orders `validateRecords` → `if (manifest.version === 2) throw` → `decideImport`, so a returning v2 revision that the origin's `recordExport` history already knows cannot be reported `duplicate`. `applyCharacterChats` rejects only by delegation: it runs its own `validateRecords` (which accepts well-formed v2 through `validateBard`), copies `stagingRecords`, then the staged `applyPlaySet` throws before `db = copy(database)`. That is correct and non-mutating today (the test asserts the receiver is byte-identical), but the protection is one refactor away from disappearing; an explicit check in `applyCharacterChats` would be cheap insurance. The replaced test is confirmed by the repro log, which still lists the old "Bard memory and slot revisions participate in chat deduplication" name.

**D-R3-4 — fixed by trace only.** `workspacePath(saved.path)` is wrapped with the page path and the outer `Memory save <id>:` prefix; `decodeMemorySaveChat` in `playSetMemoryMaterials` is wrapped with `<slot>/chat.bin`. No supplied test asserts the page-path text (the damaged-page test only matches `/slot/`), and the vitest suite is unlogged.

**D-R3-5 — fixed; test sensitive.** `recordKind === 'module' && /^\/assets\/\d+\/1$/` makes module asset paths whole-field; `asset()`'s own regex permits spaces. Pre-fix the extractor would have requested `assets/module`, which the test forbids.

**Originals and false acknowledgement.** Every traced mutation path still works on `copy()`/`clone()` output; capture writes only to the temp directory; the sanitized slot `chat.bin` replaces only the export block (the unsanitized staged copy stays in `blocks` but is never referenced by the manifest, so `writePlaySetArchive`, which iterates `expectedEntries(manifest)`, cannot emit it). No stored generation can now carry `characterChats: true` for a v2 manifest. The inventory doc now records the promptText exclusion, local-ID exclusion from revisions, Painter/gallery normalization, the gallery owner backfill, the "fuller copy is appended" policy and the v2 rejection, closing most of R4 §4.7; it does not yet record the origin-side consequence below or the receiver hydration preconditions.

## 2. New findings

**D-R4-1 — A narrower return of an unchanged chat appends a gallery-stripped copy on the origin (proved by trace; not covered by any supplied test; originals intact; direct residual of the accepted D-R3-3 policy).**
Origin A has `sender` with chats `ch` (gallery slot `sourceChatId:'ch2'`) and `ch2`, and has only ever exported `[ch, ch2]` (G, via `recordExport`). B receives (new card; the slot's `sourceChatId` is remapped to Y_B). B exports `[X_B]` alone: `character()` calls `selectTransferGallery(ch, new Set([X_B]), …)`, the slot's owner Y_B is not selected, so the record has no slot. On A, `applyCharacterChats`: `matchingCharacters` resolves `sender` through G; the incoming chat id is X's inherited portable id; the staged fingerprint is computed against the *incoming* chat set (`{…generation, ids: stagedIds}`) and has no slot. Candidate `ch` has no `risuTransferSource`; `generations` = [G]; `chatFingerprint(ch, G, …)` projects against G's own set `{ch, ch2}`, keeps the slot, hashes differently; no other generation exists → `ch` is appended again as a copy minus its gallery slot, `mode:'new'`. A ends with `ch`, `ch2`, `ch′`. The asymmetry is that the staged side projects against the incoming selection while the candidate side projects against each legacy generation's selection. R4 §2 offered this projection as the alternative fix and it was not taken. Fix: in the legacy loop, project the candidate with the incoming chat set translated through `legacy.ids` (`new Set(manifest.items.filter(chat).map(i => legacy.ids[i.id]))`) instead of, or in addition to, the generation's own set; this leaves the receiver-side "fuller copy" behaviour unchanged (a slot-less old copy still mismatches a slot-bearing arrival) and makes narrower returns deduplicate. Test: export wide once, receive on B, return narrow, assert `duplicate` and two chats on A.

**D-R4-2 — Hydration demands are unstructured (low; design).** The planner reports hydration needs as string errors, one candidate at a time (after the host hydrates the first, the next cold candidate throws on retry), in English while sibling user-facing errors are Korean, and the character variant carries no character id. A typed error exposing `{characterId, chatId}` — or an upfront scan of all mapped cold chats on the target card — would let a host hydrate and retry without string parsing. Not a correctness defect.

No defect was found in the archive writer/reader or the memory capture beyond what R4 already carried.

## 3. Unverified risks (hypotheses; not executed)

- **Cold-stub representation on receivers.** Whether the app's cold-storage stub retains `risuTransferSource` decides behaviour: if it does, repeat receipts of an unchanged chat still return `duplicate` via the first lookup; if it drops it, every receipt touching a cold-stored received chat now demands hydration instead of silently duplicating (R4's H-R3-3, now surfaced as an error — better, but a UX cost the host must plan for).
- **Fingerprint cost.** Each incoming chat now hashes every candidate under every generation that maps it; bounded by exports/receipts per chat, but a chat exported or received hundreds of times will hash hundreds of times per receipt.
- **Carried from R4, untouched:** H-R3-1 (Painter/inlay identity bound to inlay record metadata across devices; still only same-stub tests), H-R3-2 (pre-`inlayOrigins` received chats), H-R3-4 (Painter text fields only regex-scanned), H-R3-5 (H3 slot-embedded anchors/gallery ids, H4, H5 `appliedHash` ignores Bard files, H6 msgpack byte stability).
- **Structural asset entries holding URLs.** By trace, a module `assets[N][1]` or `additionalAssets[N][1]` value of the form `https://…/assets/x.png` is neither whole-field nor `external`; the extractor then requests local `assets/x.png` and reports a spurious missing asset. Deterministic in code; whether real data contains such entries is unknown.
- **Verification gaps:** strict-TS identity of the reviewed tree; the two vitest suites (archive, memory) have no supplied run; D-R3-4's page-path wrapping has no asserting test.

## 4. Integration gates (acknowledged; kept visible, not counted as new bugs)

1. **v2 gating must also happen at `prepare`.** `validateManifest`/`verifyArchive`/`openPlaySetArchive` accept v2 (required for export round-trips), and the `ImportHost.prepare` contract verifies and stages all dependencies before `apply`. Until the journaled receiver exists, a host must reject v2 at `prepare` — before staging Bard blobs and before any host-side duplicate check that consults `decideImport` against origin generations (which do contain v2 export revisions) — otherwise the planner's throw is reached only after full staging, or bypassed entirely by a prepare-time `duplicate`.
2. **Hydration before apply** for both planners; `applyPlaySet` has no hydrate error and will `branch` on a cold-changed `appliedHash`, which is safe but creates a second set.
3. **Staged media cleanup** on `duplicate`/partial dedup; the planner still provides no unused-id list.
4. **Existing-card gallery merge/surfacing** (character-level excerpts still dropped without record).
5. **`recordExport` after every successful archive write** — without it the origin can never deduplicate returns (the legacy loop is generation-driven).
6. **Gallery identity policy**: document D-R4-1 or adopt the incoming-set projection before fingerprint dedup is relied upon.
7. Unchanged: journaled v2 receiver with `ImportQueue`; ID relinking in `chat.bin`, `risubard-save.json`, pages/receipts, wiki `source_messages`, Painter anchors; API binding defaults per the `nodeOnlyModelModeLock` note; UI/transports; `cleanup()` wiring; no-generation-during-export; Windows run of the vitest suites with a supplied log.

## 5. Verdict (export/archive and planner scope only; physical installation HOLD stands; no release approval)

The scoped R4 fixes are correct as implemented: D-R3-1, D-R3-2, H1 and D-R3-5 are proved by trace and by tests that would fail pre-fix (the repro log demonstrates sensitivity for D-R3-1), D-R3-4 is proved by trace only, and D-R3-3 is a consistent documented policy. No traced path mutates a caller database, slot file or source chat, and no planner can any longer record a v2 revision as received. The one new proved finding (D-R4-1) is the origin-side mirror of the accepted gallery policy — an extra, stripped copy with the original untouched — and is fixable in the same loop R4 just introduced. The receiver, host wiring, strict-TS state of this exact tree and the vitest suites remain unverified or unimplemented; the gates in §4 are prerequisites, and gate 1 is new in emphasis: the planner-level v2 rejection is necessary but not sufficient once a host stages before applying.
