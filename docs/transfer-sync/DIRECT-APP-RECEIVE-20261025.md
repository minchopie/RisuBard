# NAS·GitHub 자료를 앱에 직접 받기

## 요구와 범위

GOAL: NAS·GitHub에서 선택한 `.risuplay`를 다운로드 폴더 저장/별도 가져오기 없이 앱으로 반영한다. MUST: 기존 공통 가져오기·검증·영속 수신함·종료 복구 재사용, 기능별 모듈 소유권과 재적용 검사. KEEP: 기존 대화·캐릭터·API·설정·Wiki·저장 슬롯·화면 선택, 기존 파일/USB/공유 기능. VERIFY: 수신 의도 재시작 보존, 생성 중 대기, 동명 대상 선택, 반복 수신, 일시 잠금 재시도와 실제 저장 경로.

기존 **내 기기 자동 동기화 → 이 기기에 다운로드**는 이미 NAS 변경을 앱에 직접 반영한다. 이번 수정은 별도의 **저장된 파일 목록 → 내려받기 → 수신 목록에서 가져오기** 절차를 **앱으로 받기** 한 번으로 연결한다. 자동 동기화 엔진이나 앱 DB 저장기를 새로 만들지 않는다.

## 실제 흐름

1. NAS·GitHub 목록에서 **앱으로 받기**를 누른다.
2. 서버가 기존 방식으로 내려받고 검증한다. 수신 원본과 `applyRequested: true`를 앱의 기존 `play-transfer` 수신함에 저장한다.
3. 기존 3초 수신 폴링이 생성·가져오기·저장 잠금·열린 알림을 확인하고 `receiveTransfer(id, true)`를 실행한다. 생성 중이면 기다리며, 앱을 종료해도 요청이 남는다.
4. 같은 캐릭터가 있으면 기존 대화는 유지하고 받은 대화를 추가한다. 동일한 자료의 반복 수신은 기존 중복 검사로 처리한다. Wiki·슬롯 적용도 기존 arm/save/finish와 복구 경로를 사용한다.
5. 동명 대상이 여러 개면 팝업을 띄우지 않고 자동 적용 요청만 해제한다. 수신 원본은 유지하며 수신 목록의 기존 **가져오기** 버튼에서 사용자가 대상을 고른다. 다른 수신 항목이 이 항목 때문에 계속 막히지 않는다.

완료는 실제 finish 이후 수신 목록의 **가져오기 완료**로 표시한다. 서버에서 파일 받기를 마친 것과 앱 적용 완료를 구분한다. 앱 데이터 저장을 위한 내부 임시 파일·수신 원본은 필요하지만, 사용자가 Downloads에서 파일을 찾거나 다시 가져올 필요는 없다.

네이티브 USB·Wi-Fi 브리지만 오류인 경우에도 독립된 NAS·GitHub 수신함 처리는 계속한다. 네이티브 오류 자체는 기존 상태 표시로 남기며, 저장 잠금이 있으면 적용을 강행하지 않는다.

파일로 저장/파일 열기, 구 앱 JSON 호환, USB·등록 Wi-Fi·시스템 공유의 기존 흐름은 보존한다. 구 JSON 목록은 **JSON 파일로 저장**으로 표시해 직접 반영과 구분한다. 구 JSON의 가져오기 방식을 이번 변경으로 대체하지 않는다.

## 모듈과 연결 경계

| 파일 | 역할 |
|---|---|
| `src/lib/Setting/Pages/TransferPanel.svelte` | NAS·GitHub 앱 수신 버튼/상태, 기존 UI 연결 |
| `src/ts/transfer-sync/playTransfer.ts` | 공통 수신 폴링·기존 가져오기 연결, 일시 잠금 재시도 |
| `server/node/transfer-sync/transfer-remote.cjs` | 기존 NAS·GitHub 검증 후 적용 요청 전달 |
| `server/node/transfer-sync/play-set-service.cjs` | 기존 수신 기록에 선택 필드 보존, 자동 대상 선택 보류 |

모두 기존 `transfer-sync` 모듈 소유다. 새 런타임 플러그인/중복 엔진은 만들지 않는다. `docs/fork-modules/features.json`은 **전체 포크 패치**의 기능별 소유권, `manifest.json`은 파일·패치 해시를 관리한다. 공유 원작 파일의 훅은 기존 `host-bridges` 등 각 모듈이 담당한다. 모듈은 원작에 다시 붙이는 **소스 패치 묶음**이며 임의로 기능을 끄고 켜는 독립 플러그인 방식은 아니다.

## 이전 QA에서 발견한 일시 잠금

자동 NAS 작업의 순간적인 423 `NAS_SYNC_BUSY`가 수동 전송을 즉시 실패시키던 경로도 이 수신에 영향을 준다. 원격 전송은 서버가 작업을 시작하기 전에 거부한 경우에만 500ms 간격, 최대 30초 동안 기다린다. 응답에 durable `transaction`이 있거나, 클라이언트의 적용 transaction이 처음부터 있거나 대기 중 변경되면 다시 보내지 않는다. 네트워크 오류·인증 실패·서버 작업 실행 후 오류는 재전송하지 않는다. 서버의 적용 검증과 잠금은 유지한다.

## 검수 기록

실제 Claude CLI 구독 세션 `e02eff5e-a278-4212-9a96-45631b65ddc3`, Fable 5.1 high와 소스를 읽어 설계를 검토했다. 영속 요청 필드, 기존 폴링 재사용, 동명 대상 자동 보류, 일시 잠금에 한정한 재시도를 반영했다. 코드·시험 결과 재검수 및 최종 검사 수치는 아래에 기록한다.

- 실제 Claude 코드 검수: **APPROVE, with limits**, 소스/표본 검사에서 차단 결함 없음. 구 JSON 백업 재시도·기기 실행·전체 원작 실행 검증은 이 승인의 범위가 아니다.
- 마지막 브리지 오류 경계·동시 실행 검사·최종 로그/모듈 문서까지 재검수해 **최종 APPROVE**. Claude의 최초 동시 실행 우려는 실제 busy 재검사와 재현 검사 확인 후 철회됐다. 모델의 기기 조작/운영 NAS 검증은 아니다.
- 클라이언트 전송·동기화 검사: 12파일 94개 통과. 수동 클릭/자동 수신 경합도 기존 busy 재검사로 prepare·추가가 한 번임을 별도 검사했다.
- 서버 전송·동기화 검사: 22파일 199개 통과, 1파일/1검사 기존 skip. 실제 격리 HTTP 서버 재시작 후 적용 요청 유지·채팅 저장·복구 포함.
- 타입 검사: 오류 0, 기존 CSS 경고 8. 웹 빌드·공개 경계 검사 통과.
- 전체 모듈 관리 파일 470개/11모듈, 기준 v0.9.71 및 기존 호환 대상 v0.9.81에 **STRUCTURAL_PASS**. 파일 소유권·패치 적용·소스 보존 검사이며 원작 두 대상 전체 실행 검사를 새로 한 결과는 아니다.
- 증거: `tmp/direct-app-receive-20261025/`의 Claude 응답·전후 소스·검사 로그·재적용 report. 실제 기기/운영 NAS는 이 변경 소스로 시험하지 않았다.

현재 설치된 0.9.94 및 실사용 데이터는 이 소스 작업으로 변경하지 않는다. 새 설치 파일·실기기 성공·정식 릴리즈로 간주하지 않는다.
