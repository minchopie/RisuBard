# 0.9.96-ver3

## [BardWiki] 서브모델 지시문을 호출 종류별로 시스템 메시지 앞에 둠

- 대상: 원작 안정판 v0.9.96 `97ea0351120b2a6decba8985e6c8c3cef6517ddf`. 0.9.96-ver2에서 `bardwiki-cache-prefix` 모듈만 바꿨다.
- confirmedMessages를 싣는 위키 기록(`bardwiki-analysis`)과 정본 갱신(`bardwiki-canonical-update`) 요청은 이제 시스템 메시지에 고정 머리말과 **그 호출 종류의 고정 지시문만** 싣는다. 위키 기록 종류(첫 요청, 재요청, 추가 분석 재분석)는 기록 지시문, 정본 종류(묶음 요청, 재요청, 한 대상 재시도, 마크다운 재시도)는 정본 지시문이다. 다른 작업의 지시문은 요청 어디에도 실리지 않는다. 작업 이름 줄과 작업 구분 태그는 없앴다.
- 사용자 메시지는 그대로 `<confirmedMessages>` → `<request_instructions>` → `<request_data>` 순서다. `<request_instructions>`에는 호출마다 달라지는 조각(로어 참고 안내, 과거 턴 재분석, 이야기 아크, 재요청 안내, 마크다운 재시도, 프롬프트 스키마)만 원래 순서대로 남고, 없으면 비어 있다.
- 지시문 문구는 고치지 않고 자리만 옮겼다. 머리말은 0.9.96-ver2 머리말에서 한 문장을 "시스템 메시지 끝의 고정 지시문과 `<request_instructions>`가 함께 이번 요청의 지시"라는 뜻으로 바꾼 것이다. 위키 기록 재요청에는 고정 지시문의 마지막 문장을 아래 지시로 바꾼다는 한 줄이 붙는다.
- 얻는 것: 같은 종류의 호출은 턴이 바뀌어도 시스템 메시지 전체가 바이트까지 같아, 공급자 캐시가 턴을 넘어 재사용할 수 있는 앞부분이 130 → 기록 약 4,718 / 정본 약 2,913토큰으로 늘어난다. 한 턴 안의 같은 종류 호출(첫 요청과 재요청, 정본 묶음과 재시도)은 시스템과 원문 증거를 함께 공유한다.
- 내주는 것: 한 턴의 위키 기록 호출과 정본 호출은 이제 머리말(약 148토큰)만 공유한다. 0.9.96-ver2에서 두 호출이 함께 쓰던 원문 증거 블록(증거 크기만큼, 숨김 기록을 뺀 뒤 실제 기록에서 약 1,000토큰)은 서로 공유하지 않는다.
- 요청 크기: 0.9.96-ver2보다 호출마다 18토큰(머리말 차이) 크고, 위키 기록 재요청만 46토큰 크다. 캐시가 맞지 않는 턴의 비용은 0.9.96-ver2와 거의 같다. 앞 판(두 작업 묶음)에서는 기록 약 +2,870, 정본 약 +4,675토큰이었다.
- 고정 지시문은 같은 채팅에서 위키 프리셋, 캐릭터·채팅 위키 가이드, 작성 언어·문체 설정, 플레이어 이름이 바뀌지 않고, 그 안에 턴마다 값이 바뀌는 매크로가 없을 때만 턴마다 같다. 과거 턴 재분석은 기록 가이드를 재분석용으로 따로 만들므로 기록 지시문이 일반 턴과 다르다(정본 지시문은 같다).
- 'AI 분석 토큰 상한' 처리: 새 배치가 18~46토큰 크므로, 예전 배치는 들어가고 새 배치는 들어가지 않는 경우에는 그 요청을 0.9.96-ver2와 같은 배치로 보낸다(보내는 자료는 같다). 정본 갱신 묶음 나누기와 호출 수·순서는 바뀌지 않는다.
- 리부트·일괄 분석 요청과 confirmedMessages가 없는 요청(정리·기준 합성·v1/v2 분석 등)은 예전 그대로다.
- 측정(기본 위키 프리셋, 한국어, o200k, 시험용 한 턴 증거 808자 / 442토큰): 기록 고정 지시문 25,717자 / 4,558토큰, 정본 고정 지시문 15,463자 / 2,753토큰, 머리말 781자 / 147토큰(0.9.96-ver2 머리말 671자 / 130토큰). 요청 토큰 0.9.96-ver2 → 이번: 기록 5,169 → 5,187, 기록 재요청 5,226 → 5,272, 추가 분석 재분석 5,226 → 5,244, 정본 묶음 3,526 → 3,544, 정본 재요청 3,515 → 3,533, 마크다운 재시도 3,561 → 3,579.
- 실제 모델 응답 품질과 공급자 캐시 적중은 아직 확인하지 않았다(빌드·검사만).
## [BardWiki] 서브모델 증거에서 숨김 기록(HTML 주석)을 뺌

- 카드가 응답마다 붙이는 숨김 기록(MGE 카드의 `<!--MGE_STATE … MGE_STATE-->` 등 HTML 주석)은, MGE 카드처럼 카드 자신의 editprocess 정규식이 그런 주석을 본 요청에서 지우는 카드라면 본모델이 읽지 않는다. 그런데 위키 기록·정본 갱신 요청의 증거(`confirmedMessages`)와 최근 맥락(위키 검색어·이름 찾기에 쓰임)에는 저장된 원문이 그대로 들어가 이 기록이 서브 요청의 절반 이상을 차지했다.
- 이제 `memoryAnalysisClient.ts`의 분석 입구(`confirm`, `schedule`)에서 증거 메시지와 최근 맥락 메시지의 HTML 주석(`<!--`부터 `-->`까지, 바로 앞 줄바꿈 1개 포함)을 지운 사본을 서브 분석에 넘긴다. 이 카드의 기록만이 아니라 **모든 카드**의, 사용자 메시지를 포함한 **모든** 증거·맥락 메시지에서 HTML 주석을 전부 지운다(첫 메시지 증거만 예외). 닫히지 않은 `<!--`가 있으면 그 자리부터 그 메시지 끝까지가 증거에서 빠진다. 일반 턴, 과거 턴 재분석, 추가 분석, 리부트·일괄 분석이 모두 이 입구를 지나므로 한 번씩만 적용된다.
- 카드 정규식을 그대로 돌리는 방식(processScript editprocess)은 CBS·플러그인 처리기·현재 열린 채팅에 따라 결과가 달라질 수 있어 쓰지 않았다. 대신 글자만 보고 정하는 순수 함수라 한 턴의 모든 서브 요청과 재시도에서 증거가 바이트까지 같다.
- 바뀌지 않는 것: 저장된 메시지, 메시지 ID·역할·순서, 확인 표시, 카드, 본모델 요청, 로어북 활성화(원문 그대로 검사), 첫 메시지 증거(이미 editprocess를 거침), 0.9.96-ver3 앞 절의 요청 배치, 호출 수·순서. 주석이 없는 메시지는 그대로 보낸다. 사용자 직접 위키 명령의 현재 메시지 자료는 이번에 바꾸지 않았다.
- 측정(o200k): 실제 채팅 내보내기(2026-10-09, 기록 2건)의 마지막 턴 증거 블록 3,802자 / 2,497토큰 → 1,581자 / 1,083토큰. 카드 editprocess 정규식 2개를 적용한 결과와 바이트까지 같다. 검토자가 최근 판 카드의 실제 요청 기록에 이 판의 함수를 적용해 잰 결과: 증거 블록 14,287 → 982토큰(응답 메시지 21,785 → 1,147자).
- 실제 모델 응답 품질과 기기 적용은 아직 확인하지 않았다(빌드·검사만).
